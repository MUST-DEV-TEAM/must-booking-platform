# Milestone 11.5: Pre-Release Fixes (before Milestone 12)

Status: **Closed for v1 (2026-08-05)** — see "Close-out" below.
Depends on: Milestone 11

## Goal

A focused milestone between Milestone 11 (closed) and Milestone 12 (Integration & Initial Release Readiness): real, concrete gaps and a real payment-gated Clock booking flow, found and scoped directly with the owner rather than assumed. Numbered outside the normal 0-13 sequence deliberately (owner's explicit call, mirrors how Milestones 4/5/8 were reopened for the same kind of real-gap reason).

## Kickoff decisions (2026-08-05)

- **Main Dashboard** is an aggregate KPI/summary view only (totals across properties) — not the full merged operational lists (Reservations/Payments/Guests stay per-property, reached as today).
- **Clock's role**: MUST is a middle layer — holds a local mirror of Clock's rooms/rates/availability, double-checks with Clock before confirming, and Clock pushes changes back via webhook (bookings from Booking.com/Airbnb via Clock's channel manager, direct rate edits, etc.) to keep the mirror current.
- **Clock-origin data** shows inside the *existing* Accommodations/Reservations sections with a "ClockPMS" tag, not a separate nav section.
- **Deposit accounting**: originally planned as a separate `deposit=true` Clock folio (per the legacy plugin's ADR-0003 prior art), but real-sandbox testing (2026-08-05, Task 5) showed Clock nets *any* posted payment on *any* folio into the booking's own aggregate `Balance` — there's no Clock-side way to post a real payment that doesn't count toward it. Revised: a plain booking note records the deposit (zero effect on `Balance`, matches "staff reconciles manually"), at the cost of the deposit not being a real financial record inside Clock. See Task 5.
- **Payment-gated booking**: pay-before-confirm, matching the legacy plugin's own proven pattern (ADR-0001, "Payment-first Clock fulfillment") — pending local reservation + payment persisted before any Clock call; Clock booking only created after the gateway's own webhook confirms payment (never from a browser redirect, which is non-authoritative); a Clock failure *after* payment succeeds goes to the existing `ManualReviewItem` mechanism (Milestone 11 Task 12), not a silent retry or auto-refund.
- **Cancellation/refund policy**: automatic Clock cancel + PokPay refund if requested ≥21 days before arrival; within 21 days, self-service cancellation is blocked and the guest must contact the hotel for staff to handle manually. 21 days is a per-property default, configurable in settings.
- **Multi-room bookings**: guest can book several rooms in one order; per-room guest name is optional (falls back to the primary guest's name). Implementation is free to create one Clock booking per room (matches Clock's own model — "1 RoomType has 0..n Rates" style per-room structure, and the legacy plugin did the same, ADR-0001: "Multi-room provider creation is not one atomic operation") as long as availability is checked and reserved atomically, all-or-nothing, locally before payment is ever taken.
- **Multi-room partial failure**: reject the whole request *before* payment if any room isn't actually available (never partially charge for what can't be delivered). If a per-room Clock create still fails *after* payment (rare, since local availability was already confirmed), only that room goes to manual review — sibling rooms that succeeded stay confirmed; no auto-cascading cancellation.

## Close-out (2026-08-05)

Tasks 1–6, 10, 11, 13, 14 are Done — all of them genuinely verified (build/typecheck, and for the payment/Clock-integration tasks, real sandbox e2e), not just claimed. That covers every v1-blocking need this milestone was scoped for, including the actual reason it exists: a real, working payment-gated Clock booking flow, and the web-to-Clock connection actually showing correct data to guests (Task 14, added after v1 scoping discussion: guest-facing availability now queries Clock live via `PmsProviderRegistry` instead of relying on a local mirror that nothing kept in sync).

**Tasks 7, 8, 9, 12 are deferred, not abandoned** — explicitly out of v1 scope by owner decision (2026-08-05), not because they're low quality or partially done:
- **7/8 (multi-room booking)**: real limitation (guests wanting 2+ rooms do separate checkouts today), but not a v1 blocker. Revisit as a near-term post-launch priority if early properties see meaningful group/family booking volume.
- **9 (Clock webhook sync)**: still blocked on Clock not documenting its webhook payload shape. Task 14 solved v1's actual need (guest-facing correctness) without it, since guest checks now go live to Clock rather than depending on a synced local mirror. Only becomes relevant again if a later version needs the local mirror itself kept current (e.g. for reporting) or if early properties' Clock accounts take bookings from other channels (Booking.com/Airbnb/walk-ins) alongside MUST — worth re-asking that question before the next milestone that touches Clock.
- **12 (Clock-origin visibility tags)**: blocked on 9 by definition, deferred alongside it.

When picking this back up, start a fresh milestone rather than reopening this one — these four are better scoped together as a deliberate "Clock multi-channel + multi-room" milestone once there's a real signal (from live usage) that they're needed, rather than kept open indefinitely here.
