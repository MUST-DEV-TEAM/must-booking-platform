## Goal

Per [ADR-0016](../../decisions/ADR-0016-guest-frontend-is-retrofitted-legacy-plugin.md) (2026-07-30): the guest-facing frontend is not a new green-field widget. It is the legacy single-tenant WordPress plugin (`MUST-DEV-TEAM/must-hotel-booking`), imported into this monorepo as `apps/wordpress-plugin` and retrofitted so its own booking domain logic, payment integration, and Clock PMS sync code are stripped out and replaced with calls to the MUST Public API, while its existing UI/templates/guest-facing look and feel are kept. Multi-tenant configuration (API base URL, tenant ID, property ID, plugin-scoped API credential) is added to its settings screen so each tenant's own WordPress install can point at their own tenant/property in the shared backend. Done means: a guest can complete a full booking end-to-end through the retrofitted plugin, talking only to the MUST Public API, with no PMS/payment credentials or booking domain logic left inside WordPress.

## Draft task areas (not final — define the real 10 tasks at kickoff; the first task must be the audit pass below, before any UI-wiring task is written)

1. Import the legacy plugin's code into this monorepo as `apps/wordpress-plugin`.
2. Audit pass: inventory every place the legacy code assumes single-tenant operation (hardcoded hotel identity, stored Clock/payment credentials, direct PMS/payment calls, its own booking state handling) — produces the concrete list the remaining tasks are scoped against, not assumptions.
3. Strip the plugin's own booking domain logic (state handling, availability checks) and replace with calls to Milestone 4's booking API.
4. Strip the plugin's own payment integration and replace with calls to Milestone 5's guest-payment API.
5. Strip the plugin's own Clock PMS sync code entirely (no direct PMS calls of any kind from WordPress).
6. Add tenant/property configuration to the plugin's settings screen (API base URL, tenant ID, property ID, plugin-scoped API credential), replacing every hardcoded single-tenant assumption found in the audit.
7. Rewire the existing UI templates (search, room selection, checkout, confirmation) to the MUST Public API responses, keeping the existing look/feel/markup as-is wherever it doesn't depend on removed code.
8. Signed-link cancellation flow (guest cancels via a signed URL, no login), matching the plugin's existing cancellation UI where one exists.
9. Credential/config security pass: confirm no PMS/payment credentials or secrets remain in the plugin's code, database options, or logs.
10. E2E test: full guest journey (search → select → checkout → confirmation → cancel) against a seeded test tenant, running the actual retrofitted plugin against a real WordPress instance.

## Explicitly not included

- A separate framework-agnostic widget for non-WordPress sites (backlog, only if an actual tenant needs it).
- Full white-labeling/theming beyond whatever the legacy plugin's existing theming already supports.
- Multi-tenant marketplace distribution of the plugin (e.g. WordPress.org listing) — each tenant's install is configured directly for now.

## Kickoff decisions

Resolved at kickoff on 2026-07-31, before writing the task table below:

- **Repo access**: `MUST-DEV-TEAM/must-hotel-booking` is accessible — Task 1 can clone/import it directly.
- **Plugin authentication model**: no new credential. Per the refinement to [ADR-0016](../../decisions/ADR-0016-guest-frontend-is-retrofitted-legacy-plugin.md), the plugin's JS calls the MUST Public API directly from the guest's own browser using ADR-0017's existing anonymous `must_guest_session` model — the settings screen only needs non-secret tenant ID, property ID, and API base URL configuration, not an issued/rotated API key.

**Revised after Task 3 correctly stopped rather than guessing (2026-07-31):** two real gaps surfaced once actual API-wiring work started. (1) No public/guest-facing availability search endpoint exists — `AvailabilityController` is staff-only (`@TenantScoped`); Milestone 4 only ever needed availability-checking *inside* `createBooking`/quote creation, once a room type is already chosen, never a public "what's available" search surface. (2) Task 6 (tenant/property/API-base-URL config) was sequenced *after* Tasks 3–5, but domain-stripping obviously can't wire calls to an API without first knowing which tenant/property/base URL to call — a sequencing mistake on my part, not a real dependency. Both are fixed by inserting a new Task 3 (public availability endpoint, reusing `AvailabilityService.getAvailability` behind a new `@PublicTenantScoped` route, exactly mirroring the existing quotes/bookings pattern; plus the tenant/property/API-base-URL config, pulled forward from the old Task 6) and renumbering everything after it down by one. The milestone stays at exactly 10 tasks.

**Revised after Task 4's review (2026-07-31): milestone grows to 11 tasks, a deliberate exception.** Task 4's cleanup surfaced that the legacy plugin's WordPress Admin back-office (dashboard, reservations, calendar, accommodations, rates/pricing, payments admin, reports, provider logs) and its Staff Portal are far more extensive than the original audit implied, and both are now broken — ~40 files still call repository factory functions (`get_reservation_repository()` and three siblings) that construct classes Task 4 deleted. None of tasks 5–10 own fixing this: 5/6 (renumbered 6/7) only cover the guest-facing payment/Clock *integration*, not the staff-side admin screens for them; 7 (renumbered 8) only covers guest templates. Rather than leave ~40 files of dead, fatal-erroring staff tooling in the repo as undocumented debt, or force it into a task it doesn't fit, a new Task 5 is inserted to remove it outright — it's pure staff back-office, not part of the guest journey this milestone promises, and Milestone 9 (Tenant Admin Dashboard, per ADR-0023's renumbering) is already building its real replacement. This pushes the task count to 11; the "exactly 10" norm exists for reviewability, and an artificial merge here would blur two tasks' acceptance criteria rather than serve that goal, so the count is allowed to grow instead.

### Task 4 review (2026-07-31) — changes requested, not yet Done

21 of the 23 audited booking-domain files were genuinely removed and `Plugin.php` was correctly updated to stop starting local inventory backfill, lock-cleanup, and availability AJAX hooks. However:

1. **Confirmed site-breaking regression**: `PaymentEngine::registerHooks()` (`src/Engine/PaymentEngine.php:2377`) calls `LockEngine::getCleanupCronHook()` directly — an immediate, eager static call, not deferred inside a hook callback. `LockEngine` was deleted by this task. `PaymentEngine::registerHooks()` is called unconditionally from `Plugin::initPlugin()`, which is hooked to WordPress's `plugins_loaded` action (`must-hotel-booking.php:62`) — meaning **every single request to a WordPress site with this plugin active will now fatal-error**, not just the booking flow. This must be fixed before Task 4 can be considered complete, regardless of which later task owns payment cleanup.
2. Two audited files were left in place and still reference deleted classes: `src/Engine/CancellationFinancialCleanupService.php` (calls `get_reservation_repository()` and `CancellationEngine::getPenaltyDetails()`, both deleted; referenced by `BookingLifecycleSyncService.php`, `PaymentRefundService.php`, `tools/lifecycle-sync-smoke-test.php`) and `src/Engine/CouponService.php`.
3. A broad sweep for the 18 deleted engine/repository class names turned up many more remaining references across Admin, Frontend, Portal, Clock/Local provider, and test files. Most of these are legitimately out of Task 4's scope (Clock/payment-specific → tasks 5–6; guest templates → task 7, already flagged by the report). But `php -l` only checks syntax, not whether referenced classes/functions still exist, so **eager references (anything reachable from `Plugin::activate()`/`Plugin::initPlugin()`/any `registerHooks()` called from those, or any other unconditional/bootstrap code path) are a correctness bug that must be fixed now, distinct from feature work correctly deferred to a later task.** Deferred/lazy references (only reached when a specific, not-yet-rewired admin screen or template is visited) are fine to leave for now.
4. `CouponService.php` is architecturally incompatible with the signed-quote model (`QuoteService` verifies an exact, server-computed total; MUST's backend has no coupon/discount concept anywhere in the schema or API). Resolved: drop coupon support from the retrofit. There is nothing to migrate it to, and per ADR-0016 the plugin should carry no domain logic of its own — a coupon UI that can no longer affect the charged total is worse than no coupon UI. `CouponService.php`, its admin screens (`CouponAdminActions.php`, `CouponAdminDataProvider.php`), and its call sites in `PaymentEngine.php`/`checkout-page.php` should be removed as part of this task's cleanup (it's an audited booking-adjacent file, not payment/Clock-specific).
