## Goal

The staff-facing `apps/web` Next.js dashboard covers day-to-day hotel operations: reservations, payments, guests, staff, and settings — RBAC-gated per `docs/TENANCY.md`. Done means: a hotel's staff can run their day (see bookings, create a walk-in reservation, handle a refund, add a staff member, adjust settings) without touching the database directly.

## Draft task areas (superseded by "Tasks" below — kept for history)

## Resolved ahead of kickoff (2026-07-31)

The owner has produced Figma designs for this dashboard (page "01 — Admin Dashboard", 22 sections) ahead of this milestone starting. Reviewed node-by-node against current backend decisions; three conflicts were found and resolved with the owner before kickoff, so the real task table (written when Milestone 8 closes and this milestone actually starts) doesn't have to re-litigate them:

- **Coupons (design section 10, fully designed: list/create/edit/usage/expired states) is out of scope.** Milestone 6 Task 4's review already established coupons are architecturally incompatible with the signed-quote model (`QuoteService` verifies an exact, server-computed total; no discount concept exists anywhere in the schema/API). The design section is not built; the backend decision stands.
- **WordPress Plugin settings (design section 14) is trimmed to "Connect + basic settings" only.** The full designed flow (Connect Website → Select Hotel → Choose Frontend → Configure Branding → Create & Map Pages → Verify & Publish) is a page-builder-style feature, materially bigger than ADR-0016's decision to keep the legacy plugin's existing UI as-is and only add tenant ID/property ID/API-base-URL fields to its settings screen. Only the "Connect Website" + basic tenant/property/API-URL settings piece is in scope — it matches what Milestone 6 Task 3 already built. "Choose Frontend / Configure Branding / Map Pages" is parked as a future idea, not built now, and would need its own ADR revisiting ADR-0016's scope if it's ever picked up.

This keeps the "Explicitly not included" boundary above intact rather than letting billing logic leak into two milestones.

Overall, the design was assessed as generally reliable for kickoff purposes beyond these three conflicts — deep and consistently structured (states, empty/error variants, prototype overlays throughout) rather than throwaway, per the owner.

## Kickoff resolved (2026-08-02, brainstormed with the owner)

Extensive Q&A before writing tasks, grounded in reading the actual schema/endpoints rather than assuming — several real gaps surfaced that the draft above couldn't have anticipated:

- **The "trial countdown" line in the old draft's task 10 is dropped.** Milestone 2's actual decision was self-serve signup landing directly on the permanent Free plan with no trial clock — that line was a stale leftover from before that decision.
- **Booking detail is a client-side panel, not a new endpoint.** `BookingProjectionService.list()` already returns full guest contact info, room/rate names, status, payment method, total, and timestamps — everything a detail view needs.
- **Payments screen uses the existing aggregate booking status**, not per-booking transaction history — no new backend for that.
- **Guests are already deduplicated by email at the database level** (`resolveGuest()` in `local-pms.provider.ts` does a real find-or-create with a race-safe `ON CONFLICT`), so a guest directory is a straightforward aggregation query, not new dedup logic.
- **`PAY_AT_HOTEL` bookings currently have no way to ever be marked paid** — no `Payment` row is ever created for them. Rather than building a narrow "Cash for walk-ins" feature, this milestone builds one general **manual-payment-recording action** usable both at walk-in creation and for settling an existing online `PAY_AT_HOTEL` booking later. This also makes the Reports revenue metric accurate across every payment method.
- **The property-role-template/capability system (Milestone 1) is far more built than the draft assumed**: `PropertyRoleTemplatesService.createCustomTemplate()` already exists as a service method, just has no controller route; two built-in templates ("Property Manager", "Front Desk") are auto-seeded per property. But **no endpoint lists available templates for a property at all** — a real gap this milestone closes.
- **Reservations, bookings, and refunds currently have zero capability gating** — only Staff/Settings/Reports/Guests management are capability-gated today (5 capabilities total: `staff.invite`, `staff.manage_permissions`, `settings.manage`, `reports.view`, `guests.manage`). Since this milestone builds real custom role templates, two new capabilities are added — `bookings.manage` (gates booking creation) and `payments.refund` (gates refunds) — so a custom template can actually restrict who does what.
- **Booking rules are a mix of enforced and informational.** Min/max length of stay and the advance-booking window are actually validated (rejects a quote/booking that violates them, both guest-facing `QuoteService` and the new staff booking-creation path). Check-in/check-out times are informational display fields only, not validated against booking dates. All three are Property-level only, no per-room-type overrides (no proven need yet).
- **A real Overview home screen is in scope**, not just a shell that lands on Reservations — KPIs (today's arrivals/departures/in-house/occupancy), a needs-attention panel (derived from non-happy-path `BookingStatus` values: `MANUAL_REVIEW`, `PAYMENT_FAILED`, `AVAILABILITY_FAILED`, `PMS_REJECTED`, `PMS_UNKNOWN_RESULT`), recent activity, quick actions — matching the Figma "01.0 — Dashboard / Overview" reference screen's actual structure, not a stripped-down version of it.
- **Real in-app notifications are in scope**, not just a pull-based activity log — a new `Notification` table, triggered by: new booking created (guest or staff), a booking entering a needs-attention state, a refund issued, and the staff-seat cap being reached (Milestone 2's plan-usage API). In-app only for v1, no email.
- **A tenant can have multiple properties, but every existing operational endpoint is already property-scoped** (`/tenants/:id/properties/:id/...`) — the dashboard gets a property switcher (pick one, everything below scopes to it), not cross-property rollup views. No new aggregation-across-properties backend needed anywhere.
- **Nav items are hidden by role, not shown-then-403'd** — `PropertyStaff` sees Reservations/Calendar/Guests/Payments (day-to-day operations); Staff/Settings/Reports are Owner/Admin only, matching the existing backend's actual gating pattern exactly.
- **The dashboard shell reuses Milestone 8's now-fixed `packages/ui` `AppShell`/`SidebarNavigation`** (icons, brand block, user-profile footer, real desktop header) rather than rebuilding shell infrastructure — this is exactly the reuse that justified fixing it there instead of patching `/platform` alone.
- **WordPress plugin settings stay entirely separate**, per the "Resolved ahead of kickoff (2026-07-31)" note above — Milestone 6 Task 3's wp-admin screen is not part of this milestone's Settings UI at all.

**First submission reviewed, sent back — real security issue (2026-08-02).** The `price()`/`enforceBookingRules()` refactor in `QuoteService` is clean and correct: pricing and rule-enforcement are now genuinely shared between the guest quote path and the new staff endpoint, not duplicated. But `LocalPmsProvider.createBooking` stores the staff actor's real `userId` in the `guest_session_id` column (`command.quoteSessionId ?? command.staffActorId`) to satisfy that column's current `NOT NULL` constraint, since there was no `staffActorId` concept before.

This is a real authorization bypass, not a style nitpick: `updateBooking`/`cancelBooking` authorize the public, unauthenticated guest-facing `PATCH`/`DELETE` endpoints (`booking.controller.ts`) purely via `row.guestSessionId !== command.guestSessionId` — a direct string comparison against the `must_guest_session` cookie. That cookie is `httpOnly` (blocks browser JS access) but **not signed or server-bound** — any raw HTTP client (curl, not a browser) can set it to an arbitrary value, and the server trusts whatever it receives at face value. Since a staff-created booking's `guest_session_id` is now that staff member's real `userId` — a value visible to other tenant staff via `GET /tenants/:id/properties/:id/staff` (and to Owner/Admin via the memberships list) — **any party who learns that ID can forge a `must_guest_session` cookie equal to it and freely cancel or modify every booking that staff member ever created via this endpoint, through the completely public, unauthenticated guest API.** This bypasses `bookings.manage`, bypasses tenant-membership checks entirely, and is exploitable by a `PropertyStaff` account with no capabilities at all, or by anyone external who learns the ID some other way (audit-log `actor_user_id`, etc.).

Root cause and fix: `guestSessionId` on `Booking` is currently `String` (`NOT NULL`) in the schema — that's *why* a real value had to be substituted. Correct fix: migrate the column to nullable, leave it `NULL` for staff-created bookings (don't invent a substitute value at all), and let the existing `row.guestSessionId !== command.guestSessionId` check do its job — `null !== anyClientSuppliedString` is already `true` in JS, so a staff-created booking becomes correctly unreachable via the public guest endpoints with zero new comparison logic needed. `staffActorId` can still be threaded through to wherever it's actually needed (e.g. audit logging, a future staff-side booking-detail/cancel endpoint) — it just shouldn't be written into the column that guest-facing public authorization keys off of. Also: rename or drop the `skipQuoteValidation` flag's coupling to this — once `guestSessionId` is properly optional/nullable end-to-end, re-verify the `!(command.quoteSessionId ?? command.staffActorId)` guard still makes sense (it may just become `!(command.quoteSessionId ?? command.staffActorId)` unchanged, but double check the intent now that `staffActorId` isn't also standing in for the guest-session column).

**Fix verified (2026-08-02).** `guestSessionId` migrated to nullable via an additive `DROP NOT NULL` migration; the INSERT now writes `command.quoteSessionId ?? null` — staff bookings correctly get a real `NULL`, no substitute value. `staffActorId` is now properly separate and even improves the `booking.created` audit entry (previously always `actorUserId: null`, now correctly attributed to the staff creator when applicable) — a sensible byproduct, not scope creep. **First submission reviewed, sent back — real data-integrity bug (2026-08-02).** The directory endpoint itself, the migration, and the search/aggregation logic are all correct and well-tested. But `resolveGuest()`'s new conditional update for `first_name`/`last_name` uses `guest.firstName !== undefined` as its "was a value actually provided" check — mirroring the existing pattern used for `street_address`/`city`/etc. But that pattern only works for fields that are genuinely optional upstream (those use a real three-state `undefined`/`null`/value helper). `firstName`/`lastName` are not: both `booking.controller.ts` and `staff-booking.controller.ts` coerce a missing name to `''` (empty string), never `undefined` — confirmed by reading both call sites directly.
