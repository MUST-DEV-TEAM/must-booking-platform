# Milestone 12: Integration, Hardening & Initial Release Readiness

Status: Kicked off 2026-08-14, tasks defined below
Depends on: Milestones 0-11

**Kickoff decisions (2026-08-14):** scope is deliberately narrower than the original draft's general "initial version for anyone" framing. The real, immediate target: v1 solid enough for Empire Beach Resort specifically — the one real, already-onboarded, Clock-connected tenant taking real guest bookings and real payments right now — with a target of next week. Prioritized by demonstrated risk, not the original draft's generic 10-area checklist: the homelab deploy pipeline was found silently broken for 2+ days during Milestone 6's close-out (a root-owned `.git` blocked the deploy user's fetches with no alert of any kind), which is direct proof that "deploys might silently fail" and "failures are invisible" are the two risks that actually matter most right now for a live paying tenant. Explicitly deferred to a later pass (once there's a second tenant or real launch pressure): a platform-wide security audit, full metrics/dashboards, demo/seed data scripts, a general (non-Clock-specific) reconciliation job, and a full documentation pass.

**WordPress integration note (2026-07-31):** Milestone 6 (WordPress Plugin Retrofit) was paused mid-flight and Milestone 10's guest-widget tasks (individual-room picker, direct-room-entry) were deferred alongside it. This milestone's task table must include the consolidated pass that finishes both against whatever the backend looks like by this point — not assume Milestone 6 is otherwise done.

**Resequencing note (2026-08-03, ADR-0025):** Platform Billing moved from Milestone 11 to Milestone 13 (last), after this milestone rather than before — the owner wants the product functional end-to-end first, and Milestone 2's permanent Free plan already makes that possible without real billing. This milestone no longer depends on Platform Billing, and its smoke test does not include an upgrade step: tenants remain on Free through this checkpoint.

## Goal

Everything from Milestones 0-11 works together as one coherent, demoable, deployable initial version. This is **not** the fully production-hardened product (see the backlog in `docs/ROADMAP.md`) — it is the "we have something real" checkpoint: reaching this milestone done is the definition of "initial version, even if not complete" from the roadmap's framing. Platform Billing (Milestone 13) is intentionally not part of this checkpoint.

## Draft task areas (not final — define the real 10 tasks at kickoff)

1. Cross-milestone E2E smoke test: signup (Free) → configure property/rates → guest books via widget → guest pays → staff sees it in dashboard → (optional) Clock-connected tenant syncs a booking.
2. Basic observability: structured logs, error tracking, and a minimal metrics/alerting setup (source brief section 28's list, scoped down — not the full production checklist).
3. Security pass: rate limiting on public endpoints, secrets audit, dependency audit, basic SSRF/input-validation review across the API surface built so far.
4. Staging deployment pipeline (CI/CD, per `docs/ARCHITECTURE.md`'s infra list) — a real environment the owner can click around in.
5. Seed/demo data scripts (a realistic demo tenant with rooms, rates, and sample bookings) for demos and manual QA.
6. Bug-fix buffer: triage and fix issues surfaced by the smoke test and staging use across Milestones 0-11.
7. Basic reconciliation job: booking/payment consistency check (source brief section 22, minimal version) to catch the most likely real-world drift.
8. Documentation pass: `README.md`, `docs/OPERATIONS.md`-equivalent (setup/deploy/diagnose), and each milestone's file confirmed accurate against what was actually built.
9. Production activation checklist drafted (source brief section 32/36-style) — not executed, just written, so go-live is a deliberate future decision, not a surprise.
10. Go/no-go review with the owner: walk through the demoable system, confirm what's genuinely usable vs. still backlog, and confirm Milestone 13 (Platform Billing) is next, followed by production hardening, more plan tiers, WordPress migration, additional PMS vendors — see `docs/ROADMAP.md`'s backlog.

## Explicitly not included

- Platform Billing (Milestone 13) — real subscriptions, dunning, plan enforcement; tenants stay on Free through this milestone.
- Full production certification of the Clock integration (remaining source-brief deliverables/hardening).
- Legacy WordPress plugin decommissioning.
- Additional PMS vendors, multi-currency billing, marketplace features — all backlog per `docs/ROADMAP.md`.

## Task 5 security review (2026-08-14)

The review covered the API's anonymous catalog, availability, quote, booking, and guest-booking routes; the Stripe, PokPay, and Clock callbacks; the WordPress plugin; tracked configuration; dependencies; and application-controlled outbound URLs. The WordPress retrofit no longer registers the old plugin public REST routes documented in its historical integration reference: it is a server-side client of the MUST API, and no longer holds payment or PMS credentials.

Fixed in this task:

- The anonymous API surface and payment/PMS callbacks now have Redis-backed, peer-IP rate limits. Limits are scoped by endpoint and tenant/property where applicable; caller-provided forwarded-address headers are deliberately not trusted.
- Clock SNS callbacks now require the connection's exact encrypted `snsTopicArn` value before accepting a valid SNS signature. This closes the previously missing source binding: a message signed by another legitimate AWS SNS topic is rejected and is not queued or stored.
- The dashboard's direct Next.js dependency was updated to 16.3.1, removing the dependency-audit findings inherited through its prior `sharp`, `postcss`, and `nanoid` tree. `pnpm audit --prod` subsequently reported no known vulnerabilities.

Checked and retained:

- Stripe verifies its raw body with the configured Stripe webhook signature before tenant/database work. PokPay has no separately documented webhook shared secret; its callback accepts no payment assertion and only succeeds after an authenticated PokPay order reread, exact local order/session binding, amount/currency match, and idempotent state transition.
- API guest return URLs are exact-origin checked against the property's configured public origin. The WordPress API origin is configured only by a WordPress administrator and is restricted to HTTPS (apart from local development), without credentials, query, or fragments. Clock SNS certificate/confirmation fetches are restricted to AWS SNS HTTPS hosts.
- No tracked `.env`, private-key, or provider-token value was found. The only tracked environment files are examples. Secret-like test fixtures remain in test files only.

Consciously deferred:

- Existing Clock connections must have their exact `snsTopicArn` added before their SNS callbacks can be accepted. This is fail-closed by design; no live Clock Message Channels subscription is currently configured for Empire Beach Resort, so no working production callback is interrupted. If a subscription is later enabled, its ARN must be saved with the connection first.
- Clock's configurable `host` is an authenticated tenant-integration setting, not an anonymous route. The documented integration contract also permits a deliberately configured HTTPS proxy base, so an allowlist cannot be imposed safely without an owner decision on proxy support. It remains an admin-only configuration surface; a future multi-tenant security pass should add an explicit outbound-host allowlist/proxy policy before untrusted tenants receive PMS access.
