## A1 rules and contract (before implementation)

- Capture once per property-local calendar date, after 02:00 local time, next 365 stay dates including today. A repeatable-read transaction, property advisory lock and unique snapshot identity commit the entire capture or nothing; retries/concurrent workers cannot replace the first complete snapshot. Scheduled hourly sweep uses the existing scoped property-discovery/BullMQ pattern; each property job carries tenant/property. No replay for missed historical dates. Snapshot time is explicit and is an observation after 02:00, not an asserted midnight close. Retain snapshot dates today minus 799 days through today (800 dates). Stored source/timezone makes a source or timezone change an incompatible comparison.
- Snapshot parent records source/timezone/capture time; day facts store sold confirmed room-nights and gross available nights (nullable); currency facts store confirmed nightly room revenue as exact integer minor units (nullable when immutable pricing evidence is missing). Currency revenue never sums across currencies. No new pricing engine. Reuse Reports facts, supply and immutable-night primitives. No fake room-type/filter detail: property aggregate history is shown only for unfiltered compatible property scopes.
- Pickup compares the same future stay dates against actual snapshots 1/7/14/30 property days earlier; negative changes are allowed. Missing captured stay dates mean No history yet; unknown price evidence remains Unknown. Pace uses the same lead distance versus the comparable stay dates a year earlier, with leap-day clamping. Need complete compatible prior snapshots and current live stored facts; do not derive past state from present bookings. No endpoint to request a backdated capture. Existing Reports workspace/exports carry these derived summaries.
- Refund reason: nullable fixed enum guest_request/hotel_cancellation/duplicate_payment/overbooking/service_issue/goodwill/other. Existing POST payments/refunds accepts optional reasonCode; unknown values reject before processing. UI requires a selection; note remains optional. Persist with the existing refund transaction/audit and existing command idempotency; do not change amounts, provider invocations, retry/status logic. Automated or legacy refunds remain Unclassified unless explicitly captured.
- Charge category: nullable vat/tourist_tax/service/other on pricing_charges, optional at old API callers, captured on create and fixed for that charge identity. Existing charge versions and quote/booking snapshots are not rewritten. A new charge component copies the recorded category; Reports groups classified charge components and labels legacy/null Unclassified. Every mandatory charge continues to be excluded from room revenue; classification changes reporting only.
- Guest country: optional ISO 3166-1 alpha-2 allowlist (249 assigned codes; not inferred from phone/city). Persist when supplied at booking creation, present in guest directory/profile and staff booking address form. Property-accessible guest country edits use bookings.edit plus guests.view (no guests.edit capability exists), verified email, expected version and Idempotency-Key with atomic audit. Guest identity is tenant-owned in the existing model; updates must prove the guest has a booking in the selected property. No PMS update.
- New tables carry tenant_id and property_id, composite property FK, forced exact tenant/property RLS. Existing nullable columns retain their table's current scope. Migration additive/idempotent; rollback application-first, retain captured history/nullable fields, no destructive down migration.

## A2 route contract (before implementation)

All following routes are relative to `/tenants/:tenantId/properties/:propertyId`, require settings.manage and exact property access; mutations require verified email. Every new mutation requires Idempotency-Key (1-128 visible characters), a nonnegative integer version and commits audit plus receipt atomically. Property row locking serializes changes; identical replay returns the saved response, changed intent or stale version is 409. Clock properties can edit MUST email settings: these are not Clock-owned prices or inventory.

- GET `email-template-versions/:key?language=en|sq` returns `{key,language,version,live,draft,history}`. Initial English live uses existing override or built-in; initial Albanian has no invented translation. History records wording, author and timestamp; one draft and live pointer per locale.
- PUT `email-template-versions/:key/draft` body `{language,version,subject,body}` saves a draft only. POST `:key/publish` publishes the current draft and updates the existing mail renderer's live override atomically. POST `:key/restore` body `{language,version,revision}` restores recorded wording into a new draft, never directly into live. Publication requires the guest variable and event-specific payment/refund variables in editable wording. Hotel identity and booking reference are protected generated layout blocks, so shipped defaults remain publishable; these blocks cannot be removed by an editor. Versioned English overrides remain compatible with current transactional senders.
- Existing email-templates preview remains the safe structured renderer; no arbitrary HTML. Controlled tests target only the signed-in verified user's address, require a reason, use a stable operation key and [TEST] prefix, max five per user/property/hour. Test traffic is separately identified and excluded from delivery health.
- GET `email-activity/overview` supplies aggregate actual status counts excluding tests and Unknown domain authentication; existing GET email-activity supplies paged deliveries and GET email-templates adds draft/locale readiness. GET `email-activity/:messageId` supplies scoped recorded delivery details. Retried mail uses the retained approved command and original recipient, never newly edited wording; unavailable retained commands cannot be retried.
- Configuration preserves all existing topic enablement, recipient role/staff/address rules, optional personal mute, review links and sender information before retiring the old screen. Unsupported transport/domain claims remain Unknown. Explicit CC/BCC requires actual transport support; until implemented its controls are hidden and the missing contract recorded, rather than mislabelling separate private deliveries as CC/BCC.

Additive migration rollback: deploy the previous application first and retain version/receipt evidence; no destructive down migration. Draft/history stores no credentials or sample guest addresses. Template bodies are hotel-authored content and escaped at rendering.
