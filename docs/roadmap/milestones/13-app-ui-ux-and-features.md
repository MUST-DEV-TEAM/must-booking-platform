# Milestone 13: Application UI/UX & Feature Enhancements

Status: Not started
Depends on: Milestone 12 (Integration & Initial Release Readiness — this milestone does not start until Milestone 12 is fully closed out, per ADR-0028's "no parallel milestones" decision)

**New milestone (2026-08-17, ADR-0028).** Inserted after Milestone 12 and before the Security & Architecture Audit (Milestone 14) and Platform Billing (Milestone 15), at the owner's request — a dedicated pass for application polish and feature work that Milestone 12's integration/hardening scope deliberately excludes.

## Goal

Close the gap between "functional end-to-end" (Milestone 12's checkpoint) and a product that actually looks and feels finished.

**Scope narrowed at kickoff (2026-08-23): information-architecture realignment, not screen-by-screen fidelity.** See "Why the scope changed" below.

## Why the scope changed — read this before picking up any task

At kickoff the full design was reviewed for the first time. The Figma file `zhCG5chiRQccT69cqBRLaK` has **two** pages, and the second had not previously been examined:

- `0:1` — `00 — Base & Components` (the token/component library)
- `3:2` — `01 — Admin Dashboard` (**the actual screen designs** — 23 sections, ~200 frames)

Page `3:2` does not describe the application that exists. It describes a substantially larger one. A full section-by-section review found:

- **Whole product areas designed with no code behind them at all**: Coupons (6 screens), Emails as an operational area with template authoring/preview/test-send/delivery-failure handling (8 screens), Availability as a first-class section separate from Calendar (9 screens), Notifications Center page tier (4 screens), custom roles + permission matrix + per-user overrides (12 screens), and a 10-screen Provider & Integrations section against the app's single panel.
- **Entity-model gaps, not screen gaps**: the design's Accommodations is a three-level hierarchy (Categories → Listings → Units); the app is flat "rooms and room types". The design's roles are editable records; the app's are three hard-coded constants. The design's pricing has four entities (base prices, pricing rules, rate plans, taxes & fees); the app has roughly two.
- **Cross-cutting contracts the app has no equivalent for**: a sensitive-action contract (§20) requiring validate → lock → impact → reason → confirm → execute → resolve → append-only audit for seven named actions, with six outcome states and typed-phrase confirmation for destructive ones; a responsive contract (§18) with four breakpoint tiers and a 12-check QA list; a **WCAG 2.2 AA** contract (§21) framed as a release gate.

Matching this design is multiple milestones of work, not one. **Milestone 13 is therefore scoped to structural realignment only**: make the app's navigation, routing and shell match the designed information architecture, with existing content moved into the new structure and explicit placeholder states where a designed area has no implementation yet.

**Two follow-ups this file does not decide:**

1. ADR-0028 describes this milestone as an "app polish and feature" pass. That framing is now wrong. A follow-up ADR should record that page `3:2` is the authoritative product design, that the app's IA is being realigned to it, and that the unbuilt design areas become new roadmap milestones.
2. `CLAUDE.md` states each milestone carries exactly 10 tasks. This file has 32. See "Milestone size" at the end.

## Standing constraints for every task

1. **Structure, not fidelity.** Build the route/shell/nav. Move existing content into it unchanged unless the task says otherwise. Do **not** pixel-match to the Figma frames — that is deliberately deferred.
2. **Placeholders must be honest.** Where the designed IA has a destination the app cannot yet fill, render the shared `not-available` state (Task 1) with a one-line explanation. Never ship a nav item leading to a blank page or a 404.
3. **No new backend endpoints** unless a task explicitly authorises one. Where designed content needs data the API does not return, render the placeholder and note the missing data in the PR description.
4. **Design references are node ids on page `3:2`** of `zhCG5chiRQccT69cqBRLaK`. Component names refer to the Claude-Design export inventory — see `docs/design/DESIGN_SYSTEM.md`.
5. **Access control must not regress.** The existing role model (OWNER/ADMIN/STAFF, STAFF gated by capability strings, with `accommodations`/`rates-pricing`/`staff`/`settings` owner-admin-only regardless of capability) is preserved exactly by every task here. Changing the role model is out of scope.
6. **Tasks are numbered in execution order.** Work them in sequence. Where two adjacent tasks touch the same file, the later one assumes the earlier has landed.

## Design sources

- Figma page `3:2` (`01 — Admin Dashboard`) — authoritative screen designs.
- Figma page `0:1` (`00 — Base & Components`) — tokens and components.

- Platform Billing UI (Milestone 15).
- WordPress guest flow and the WordPress plugin admin (design §14).
- New PMS vendors or payment providers — backlog per `docs/ROADMAP.md`.
