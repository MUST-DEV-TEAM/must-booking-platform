## Phase B — Duplicate guest profiles

`ADR-0030-guest-matching-phone-signal-and-merge.md` drafted and accepted 2026-09-10 — supersedes `ADR-0015-guest-matching-rule.md`'s explicit decision that phone is never a matching signal. Read it in full before picking up Task 3 or 4.

**Design agreed with the owner 2026-09-10, scope extended same day**: exact match on **both** email and phone auto-attaches to the existing guest (this already happens today via the email-only rule and doesn't need new merge machinery — it's the existing "reuse" path, just now double-confirmed). A match on **only one** of email/phone against a *different* existing guest than the other field would suggest is a suspected duplicate — never auto-merged, always flagged for a human to review and decide. Match on **neither** is a genuinely different guest.

**Extended scope**: the owner specifically asked that this apply to Clock too, not just MUST's own database — otherwise Clock keeps creating its own duplicate guest profile even after we stop creating ours. Clock's API fully supports this (confirmed against its real Postman docs, 2026-09-10): `GET /guests/search?free_text_search=...` to look a guest up, and `main_booking_guest: "<guest id>"` on `POST /bookings/` to attach to an existing Clock guest instead of letting Clock auto-create one from the inline `guest_*` fields. See ADR-0030 point 2 for the exact mechanics — this is Task 4, a genuinely separate piece of work from Task 3's local-only matching (different API, different failure modes), so it's its own task rather than folded into Task 3.

Merge mechanics (for the manual-merge action, once staff confirms two profiles are the same person):
- Staff picks which of the two profiles is canonical (kept) — not automatic, since automated canonical-selection can guess wrong (e.g. which spelling of a name is correct). This is a human-in-the-loop review, so let the human pick.
- **Moved**: every record with a foreign key to the losing guest's id (bookings, payments, any other guest-linked table) is reassigned to the canonical guest's id.
- **Merged**: canonical keeps its own field values; any field canonical has blank that the losing profile has populated gets backfilled (e.g. canonical has no phone, losing profile does → canonical gets it). No overwriting of a field canonical already has a value for.
- **Not destroyed**: the losing guest record is never hard-deleted — mark it (e.g. `mergedIntoGuestId` pointer + excluded from active guest search/list) so booking/payment audit history stays traceable back through it. Hard-deleting a guest with real booking/payment history is a bad idea in a system that has to account for money.
- A "not a duplicate, dismiss" action clears the suspected-duplicate flag without merging, for the case staff determine it's genuinely two different people (e.g. shared family phone number).

## Phase E — Rate management (last)

This is the largest item raised — today MUST has a fully local rate-plan CRUD (`apps/web/app/dashboard/[tenantId]/rate-management.tsx`, `apps/api/src/tenancy/rate-plans.service.ts`) with zero connection to Clock, and the Clock integration only ever *reads* rates (`ClockAvailabilityService`, `rateIdForRoomType()` at `clock-booking.service.ts:1065-1085`) — no create/edit/delete/assign toward Clock exists, and bookings only work cleanly today when a property has exactly one Clock rate plan.

**Meal plans/board types are explicitly out of scope for this phase** (owner's instruction, 2026-09-10) — every task below deals only with room-only rate selection and pricing.

**Kickoff done 2026-09-10.** Clock's team raised this after certification testing only had ≤10 rates per room type; their real question was "what happens with 50 rates, and what stops a room getting quoted at €0/night." Investigated against Clock's own public Postman docs (the same verified workspace used throughout this milestone) plus a real, permanent hand-built test rate plan (`RateTest-Summer2027`, 4 room types, 5 rate variants each with deliberately varied `wbe`/occupancy caps — see `docs/integrations/clock/endpoint-matrix.md` if a rate schema reference is needed) and a live diagnostic script run against `booking.must.al`'s real Clock connection (`GET /rates/` + `GET /products` for room type DBL/41994, three occupancy scenarios). Findings:

1. **Clock's own `/products` endpoint enforces `max_adults`/`max_children` server-side** — an over-capacity request comes back `available:false` with a descriptive error (`"Maximum adults allowed - 5"` etc.), *but only when* `product_search[adult_count]`/`[children_count]` are actually present on the request. Clock does not reject occupancy silently or return a wrong price; it just doesn't check at all if those fields are omitted.
2. **Clock's `/products` does *not* filter out `wbe:false` rates.** A rate explicitly marked "don't publish to the booking engine" still comes back `available:true` with a real bookable price, identical in shape to a `wbe:true` rate for the same room type. Confirmed directly: `DBL - Summer no WBE` (`wbe:false`) returned `available:true, price:11000` for a 1-adult stay, indistinguishable from the legitimate `wbe:true` `DBL - Summer` rate at the same price. **This is the actual mechanism behind Clock's "what if we picked a €0 or wrong rate" warning** — nothing in Clock's API stops an integrator from quoting a non-public rate; that filtering is entirely the integrator's job.
3. **A second, unrelated bug found by the same test**: `ClockAvailabilityService.getQuote`'s offer selection (`clock-availability.service.ts:223-228`) is `Object.values(roomType.rates).flat().find(available && no-errors)`. `roomType.rates` is a plain object keyed by Clock's numeric rate id as a string — and JavaScript enumerates integer-index object keys in **ascending numeric order regardless of insertion order**, not API response order. In all three test scenarios the code picked whichever valid rate happened to have the numerically lowest id, not the first one Clock returned, not the cheapest, not any considered business rule. In this test it happened to land on the property's original real rate (`784160`, lowest id) every time — accidentally correct here only because that rate happens to have the lowest id and no occupancy cap. A newly created promotional rate with a lower numeric id than the intended primary rate would silently win instead. This needs fixing regardless of the `wbe` fix below.
4. `QuoteInput.adults`/`.children` (`quote.service.ts:19-20`) are optional at the type level; `getQuote` only forwards them to Clock `if (query.adultCount !== undefined)`. Every *current* real call site (`quote.service.ts:84-85,112-113`) does pass them today, so this isn't an active incident, but it's a silent footgun: Clock's occupancy enforcement (finding 1) only fires because today's callers happen to always populate them, not because anything guarantees it.
