# Clock webhooks and reconciliation

Status: **IMPLEMENTED processors, durable recovery path added and corrected five times**. Code inspected 2026-09-19; durable webhook processing fixed 2026-09-19 (Milestone 21 Task 22), corrected a fifth time 2026-09-23. Five corrective reviews (Astra) found: (1) a real status-regression race and an incorrect assumption about BullMQ's `add()` semantics; (2) no exclusive processing ownership, a single shared forbidden-status list that could resurrect `FAILED`, overstated concurrency/restart test claims, and an indefinite warning-log loop instead of a durable resolution for completed-but-unreconciled events; (3) the ownership check was still a check-then-act race rather than a real fence at the business-write boundary, claim ordering had no protection against a delayed/obsolete claim stealing ownership back, and "parking" a `NEEDS_RECONCILIATION` row wrote its status and its `ManualReviewItem` non-atomically; (4) the claim-ordering signal itself (`job.attemptsMade`) was wrong under BullMQ's real stalled-reassignment semantics, and the migration's rollback guidance overstated dropping the processing columns as safe "at any time"; (5) the fourth round's own job-recreation reset was itself a blind, unguarded write that could erase ownership a concurrently-claimed new job's worker had already acquired, or clobber a racing concurrent recreator. All are fixed — see ADR-0031 (amended) for the full design — and backed by real Postgres (RLS-enforced, via the application's own runtime role) and real Redis/BullMQ integration tests exercising the actual processing paths under deterministic timing barriers, genuine BullMQ stalled-job reassignment, and forced job-recreation race interleavings driven through the real production ingestion/sweep methods — not mocks or hand-orchestrated helper calls. See Task 22 in the milestone file for exact evidence and remaining gaps. Task 22 is **In review**, not Done.

## Ingestion

`POST /clock-webhooks/:webhookPublicId` is public. `main.ts` supports SNS text/plain JSON; ClockWebhookService resolves the opaque connection ID through a narrow read-only RLS lookup, checks the pinned `snsTopicArn`, then verifies timestamp, certificate host and RSA-SHA1/SHA256 signature.

The freshness window is five minutes old / sixty seconds future. Verified envelopes update `last_webhook_received_at` (including confirmation types, not only Notification). Confirmation uses SubscribeURL; its returned boolean is currently not used to alter the 200 response.

A Notification must resolve to exactly one enabled property. Otherwise it is acknowledged/dropped with a warning. Accepted events persist in `provider_events`, deduplicated by `(connection_id, event_id)`, then enqueue `clock.webhooks/hydrate-event` before returning 200. `Subject` supplies the event type; Message is normally a single resource-ID object such as `{"booking_id":123}`.

**Reliability limit (fixed 2026-09-19, corrected twice same day, Milestone 21 Task 22 — see ADR-0031):** insert and enqueue are still not atomic — that remains structurally true of a Postgres+Redis pair — but a stored row plus failed enqueue is no longer stuck, and the durable state machine is now both concurrency-safe and ownership-safe:

- `provider_events.status`/`.attempts` transition through their full lifecycle (`RECEIVED` → `QUEUED` → `HYDRATED`/`IGNORED`, or `FAILED` once BullMQ exhausts its attempts, or `NEEDS_RECONCILIATION` — see below) via a guarded `UPDATE ... WHERE status = ANY(allowedFrom)` (`clock-provider-event-status.ts`), never an unconditional write. There is deliberately no shared default `allowedFrom` — every caller (ingestion, the sweep, the worker's claim, the worker's finalize, the `'failed'` listener) states its own explicit list, so `FAILED` never appears in one and nothing automatic can resurrect it. This is a real compare-and-swap under Postgres's row-level locking, proven against genuinely overlapping (not just sequential) transactions.
- `processing_token` is a per-attempt fencing token, reusing BullMQ's own `job.token`. The worker claims it before calling a hydration service; the real fence is inside `ClockBookingHydrationService.hydrateBooking()`/`ClockFolioHydrationService.hydrateFolio()` themselves — after their outbound Clock fetch returns (never inside a lock), the *first statement* in their effect-applying transaction is `SELECT ... FOR UPDATE` on the provider_events row, held for that transaction's lifetime. If the row isn't still `QUEUED` with this attempt's token, nothing further happens and the transaction commits empty (`{ outcome: 'ownership_lost' }`); otherwise the local effect (booking/folio upsert, guest/mapping writes, a `missing_room_type_mapping` review item) and the event's terminal status write commit together, atomically, in that same transaction. A stalled/reassigned attempt (BullMQ's own documented caveat — the same job id can genuinely be processed by two overlapping attempts) that finishes late can neither apply its effect after losing ownership nor finalize over a newer attempt's outcome — proven against real concurrent execution with a controllable HTTP-fetch gate, not sequential helper calls. `processing_attempt` additionally guards claim order itself, via `claimEventSql`'s combined token+generation comparison: no claimant yet always succeeds; a strictly newer generation succeeds and overwrites the claimant; the same generation with the same token succeeds as an idempotent no-op re-claim; the same generation with a different token is rejected; a strictly older generation is rejected. The generation is BullMQ's `job.attemptsStarted`, not `job.attemptsMade` — verified against the installed `bullmq@6` source, `attemptsStarted` increments on every real dispatch including a stalled job's genuine reassignment (`attemptsMade` only increments on genuine failure, so two overlapping activations of a job that hasn't failed yet can share it, which would let an obsolete attempt reclaim ownership). Because `processing_attempt` is scoped to one BullMQ job's lineage, ingestion/the sweep's re-enqueue for a row whose old job disappeared (`reconcileJob() === 'missing'`) resets both `processing_token` and `processing_attempt` to `NULL`, so a brand-new job's low first generation is never permanently locked out by a stale high-water mark the old job left behind. That reset (`recreateMissingJob()` in both services, built on `processingSnapshotSql`/`resetForJobRecreationSql`) is a real compare-and-swap against a snapshot taken immediately before the replacement job is created (corrected 2026-09-19, fifth review) — not a blind write: it only lands if `processing_token`/`processing_attempt` still hold exactly the snapshotted values, so a claim that lands in between (the new job's own worker) or a second concurrent recreator racing the same row can never be silently erased or clobbered; either it wins the CAS, or it safely no-ops and leaves the newer state alone. The worker never reprocesses a row that isn't `RECEIVED`/`QUEUED` (checked before doing any work).
- Ingestion and the recovery sweep both reconcile against BullMQ's *real* job state (`ClockQueueService.reconcileJob`, real Redis-verified) before deciding what to do — `Queue.add()` with an already-known job id does not restart a `completed`/`failed` job and can silently no-op. `missing` creates a job and marks `QUEUED`; `in-flight` does nothing; `failed` marks the row `FAILED` (closing the gap where the async `'failed'` listener never got to run) without auto-retrying — a flood of duplicate SNS deliveries must not silently turn a deliberate 3-attempts-then-stop exhaustion into unlimited retries, and `FAILED` requires an explicit operator action to retry (see the recovery procedure below); `completed` is durably parked as `NEEDS_RECONCILIATION` with a `ManualReviewItem`, both written atomically in one tenant-scoped transaction (the item is only inserted if the guarded status UPDATE actually affected the row; any failure inserting it rolls the status write back too) rather than guessed at or logged forever — excluded from the sweep's candidate set, so the underlying BullMQ job later aging out of retention can never silently flip it back into automatic reprocessing.
- Hydration outcomes are classified explicitly, not treated as uniformly successful: `created`/`updated`/`applied` → `HYDRATED`; `not_a_booking_folio` (never applicable) → `IGNORED`; `missing_room_type_mapping` (a `ManualReviewItem` was already recorded) → `FAILED` immediately, actionable blocked work, not worth burning retry attempts on; `no_active_connection` and `booking_not_found` (the folio-before-booking race) → throw, so BullMQ's normal attempts/backoff/dead-letter apply and the booking event gets a real chance to land first.
- The recovery sweep touches `updated_at` on every row it examines, whether or not its status changes — otherwise a batch of currently-unresolvable rows would keep being re-selected by `ORDER BY updated_at ASC LIMIT 200` forever, starving every row past the batch limit from ever being looked at.
- Reads cross-tenant under a SELECT-only `provider_events_platform_admin_read` RLS policy (ADR-0021's already-accepted pattern); every write still goes through the normal per-tenant policy via `withTenantTransaction`.

**Operator recovery procedures** (both deliberately manual, not a new admin API — see the original task's constraint against adding a general replay surface without a separate authorization/audit review):
- **`FAILED` event, confirmed safe to retry** (e.g. after fixing the underlying cause, such as confirming a catalog mapping): `UPDATE provider_events SET status = 'RECEIVED', processing_token = NULL, updated_at = now() WHERE id = '<row id>'` — the next sweep tick (or a redelivery) picks it up fresh.
- **`NEEDS_RECONCILIATION` event**: look up the row and its linked `ManualReviewItem` (`reference_type = 'provider_event'`), verify directly against Clock (`GET` the referenced booking/folio) whether the effect actually applied. If confirmed applied: `UPDATE provider_events SET status = 'HYDRATED', processing_token = NULL WHERE id = '<row id>'`. If not applied: reset it the same way as a `FAILED` retry above.

**Verification**: unit tests (`clock-webhook.service.spec.ts`, 13 tests; `clock-worker.service.spec.ts`, 39 tests) plus real integration evidence — `clock-queue.service.spec.ts`'s real-Redis suite (8 tests) proves `reconcileJob`'s four states and that `add()` does not restart a completed/failed job; `test/clock-webhook-recovery.e2e.spec.ts` (20 tests) runs a full app against a real local Postgres (RLS enforced via the actual `must_booking_app` runtime role, not a superuser bypass) and real Redis/BullMQ, exercising the actual processing/application paths (not hand-orchestrated status-only helper calls), proving: recovery of a durably-persisted-but-never-enqueued event without any SNS redelivery; the same recovery after the worker and queue service are torn down and reconstructed with fresh Redis connections (explicitly scoped as *not* a full process restart); a genuinely overlapping-transaction race (one transaction held open with `pg_sleep` while a second's UPDATE blocks on the row lock and is rejected once the first commits); **real ownership fencing under a deterministic barrier** — attempt A claims, starts its Clock fetch and is held there by a controllable gate; attempt B claims (overwriting A's token), fetches a distinguishable result, and commits it; A is then released, resumes with its own stale result, and its transaction correctly detects lost ownership — asserting the actual business effect (`bookings` row's fields, and `version = 1`, proving the `ON CONFLICT DO UPDATE` path that would set `version = version + 1` never ran a second time), not just a status field; **real BullMQ stalled-job reassignment** — attempt A's real `Worker` is force-closed mid-job (stopping lock renewal, simulating a crash) with its Clock fetch gated so it stays paused, its lock is left to genuinely expire, and a second real `Worker`'s actual `moveStalledJobsToWait()` is driven twice (BullMQ's own two-tick protocol) to force real reassignment to attempt B; only after B claims and finishes is A's gate released, and A's now-stale resumed claim is proven unable to overwrite B's token, flip the terminal status, or apply its own effect; **claim ordering at the SQL level** — deterministic generation-ordering proof (strictly newer allowed, strictly older rejected, same-generation/same-token idempotent, same-generation/different-token rejected — the exact-tie cases impractical to force reliably through real BullMQ timing); **missing-job recreation** — a fresh job for a row whose old job disappeared can claim despite a stale higher generation left behind, driven through the real sweep path end to end; **job-recreation reset cannot erase a concurrently-acquired claim** — a real snapshot, a real replacement job, a real worker claim landing in between, and a late-arriving reset call that correctly no-ops and leaves the claim and the subsequent hydration/finalize untouched; **concurrent ingestion/sweep recreation requests coordinate durably** — both real recreation methods driven concurrently via `Promise.all` for the same row, proving exactly one job and exactly one applied booking regardless of interleaving; **operator-retry path** — the documented `FAILED -> RECEIVED` reset recovers through a real sweep tick; a stale sweep snapshot and a stale worker claim that both fail to resurrect an already-`FAILED` row; **atomic parking** — concurrent parking attempts create exactly one `ManualReviewItem`, and a forced failure inserting the item rolls the status write back too, with a later attempt then succeeding cleanly; parking a real completed-but-unreconciled job as `NEEDS_RECONCILIATION`, and proving the sweep never selects it again even after the underlying BullMQ job is removed (simulating retention expiry); cross-tenant sweep reads plus RLS-denied cross-tenant writes; sweep rotation past the 200-row batch limit with 205 real rows; the migration's re-run idempotency (verified via a fresh apply from an empty database plus a direct SQL re-run); and the RLS-policy rollback's actual effect (see below).

**Migration and rollback**: two additive migrations — `20260919120000_provider_events_recovery_sweep` (the platform-admin SELECT policy) and `20260919130000_provider_events_ownership_and_reconciliation` (`processing_token` + `processing_attempt` columns, `NEEDS_RECONCILIATION` enum value — rewritten with `ADD COLUMN IF NOT EXISTS`/`ADD VALUE IF NOT EXISTS` so it is safely rerunnable; verified by a fresh apply against an empty disposable Postgres, and a direct re-execution of its exact SQL against the same database afterward with no error). No data migration; existing rows are unaffected. Rollback of the RLS-policy migration is `DROP POLICY "provider_events_platform_admin_read" ON "provider_events"` — proven directly (not just asserted): this disables the recovery sweep's cross-tenant read **entirely**, for every tenant, not merely other tenants' rows (`withPlatformAdminTransaction` never sets `app.tenant_id`, so the policy's `tenant_id = app_current_tenant_id()` branch never matches once its `current_setting('app.role') = 'platform_admin'` branch is gone). Per-tenant webhook ingestion and processing are completely unaffected, since they never rely on that policy — only automatic crash-recovery independent of redelivery is lost. Rollback of `processing_token`/`processing_attempt` is **not** safe "at any time" (corrected 2026-09-19, fourth review) — every claim/fence/clear code path reads and writes them as part of its normal control flow, so dropping them while compatible application code is still running turns every claim attempt into a hard SQL error rather than a graceful NULL-tolerant no-op. Safe ordering: stop the worker/sweep, or deploy code that no longer references these columns, first; let any in-flight attempt finish or genuinely stall out under the old code/columns; note a parked `NEEDS_RECONCILIATION` row's `processing_*` values are historical claim metadata, not required to resolve its `ManualReviewItem`, but are lost if dropped before being exported; only then is `DROP COLUMN IF EXISTS` safe. The preferred default is to retain these additive columns during an application rollback (roll the application code back instead) rather than dropping them, sidestepping this ordering entirely — see the migration file's own header comment and ADR-0031's fourth corrective update for the full guidance. PostgreSQL has no supported way to drop a single enum value; `NEEDS_RECONCILIATION` cannot be removed by a rollback migration — if ever retired, stop writing it in code and resolve existing rows via the operator procedure above, leaving the unused value permanently harmless.

The 256 KiB check uses Content-Length after parsing. The text/plain parser does not impose a streaming limit; trusted initial certificate/confirmation URLs also do not establish redirect safety. These are review findings, not claims that an exploit was exercised.

## Worker behavior

| Event | Processor | Actual effect |
| --- | --- | --- |
| booking_new, booking_guests_update, booking_update, booking_canceled | ClockBookingHydrationService | Re-fetch current detail; map room type/room; resolve optional guest; upsert booking by external ID |
| folio_update, folio_close | ClockFolioHydrationService | Fetch Base API folio; upsert separate `clock_folios` row for the linked booking |
| Other types | ClockWorkerService fallback | Log acknowledgment; no business application |

Hydration imports Clock-origin bookings as well as updating MUST-origin records. It updates dates, rooms, occupancy, amount, nightly rates and version, and stores Clock's raw status in `bookings.pms_stay_status` (shown as a stay badge in the dashboard). Clock's documented statuses map in `clock-booking-status.ts`: `canceled` to CANCELLED; `expected`, `checked_in`, `checked_out` and `no_show` to CONFIRMED. Any other status creates an `UNKNOWN_STATUS` manual-review item (once per new value): an existing booking keeps its local status, and a new booking is not imported (event FAILED, so it can be re-sent). A booking that moves to CANCELLED through hydration was cancelled in Clock itself, so staff get the cancellation email; the guest is not emailed and no refund is started. Missing room-type mapping creates manual review. These are projections, not invocations of the local inventory/payment/cancellation pipeline. Clock-only imported bookings are not direct Booking.com API integration.

A duplicate external booking upserts the same identity, but can still increment version. A missing event row/object ID or unmapped resource can end processing without a retry-producing exception. Exhausted failing jobs go to dead-letter and operational reporting; success of BullMQ processing is not proof that every event was applied.

## Scheduled reconciliation

ClockWorkerService upserts `daily-clock-booking-reconciliation` at 03:00 UTC. A global tick enumerates active connected Clock properties and creates tenant/property-scoped, date-keyed jobs:

- `reconcile-property`: ClockBookingConsistencyService reads overlap booking IDs and then each detail, comparing status/existence with local confirmed/cancelled rows over at most 31 days. An undocumented Clock status is reported as an `UNKNOWN_CLOCK_STATUS` finding rather than aborting the check. It reports/audits findings; it is not a repair/import sweep.
- `reconcile-payments`: ClockPaymentReconciliationService selects online-paid attached bookings created since the same window start; it reads deposit folios and charge-reference credit items and flags missing/mismatched amount/currency. It does not reconcile net refunds or general folio balances, or write financial corrections.

Since 2026-10-01 the checker lists a folio's credit items and matches the reference client-side, like the refund path; it no longer sends the `reference.eq` filter Clock rejects.

The separate six-hour health job detects webhook silence, queue backlog and stuck PMS operations. See [operations](../../operations/README.md) for thresholds and [architecture gaps](architecture.md#known-gaps-and-deviations) for remaining limitations.
