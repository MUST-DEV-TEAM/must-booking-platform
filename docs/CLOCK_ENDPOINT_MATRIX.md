## Notes

- **Task 6**: `ClockPmsProvider.testConnection` and the tenant-facing "Test connection" button now both run the full stack for real — HTTP client, rate limiter, circuit breaker, error classification — against the real sandbox, not just the raw Digest probe done at kickoff. Confirmed: a valid connection succeeds end-to-end, and an invalid API key produces a clean, correctly-classified failure rather than a crash or a false success. Clock's 401-on-bad-credentials body is **plain text** (`HTTP Digest: Access denied.`), not JSON — `classifyClockHttpResponse` handles both shapes.
- `room_types` and `rooms` were confirmed reachable and correctly shaped with **real data already present in the sandbox account** (e.g. room type "Standard Rooms", room "Direct Pool") — not empty-state guesses.
- The account/subscription ID pair in the URL path (`172528`/`16307` for this sandbox) — which one is the "Clock account ID" vs. "subscription ID" per source brief section 8's terminology is not yet disambiguated; both are opaque path segments as far as the HTTP client (Task 4) is concerned, so this doesn't block implementation, only the deliverable docs' precision.
- `/rates_availability`, booking creation, and guest search remain the highest-priority endpoints to confirm for real (Tasks 7, 8, 10) — this table will be updated as each is actually exercised against the sandbox, not assumed from the legacy plugin's changelog prose.
- **Task 11**: No real Clock Message Channels (SNS) subscription exists for this account — configuring one requires Clock account-dashboard access outside this session's reach, so genuinely AWS-signed live traffic could not be captured. What *was* verified for real: the full webhook HTTP flow (routing, RLS-carve-out lookup by `webhookPublicId` across both `integration_connections` and `property_integration_connections`, dedup, BullMQ enqueue) end-to-end using a real, locally-generated RSA key pair to produce genuinely valid SNS-shaped signatures, with only the literal "fetch cert bytes from AWS" network call stubbed (the SSRF-protecting hostname check itself still runs unstubbed and was tested against both real and fake AWS host patterns). Clock's own event payload shape (the JSON string inside SNS's `Message` field) is unconfirmed — the source brief doesn't specify it and no live event has ever been captured, so `ClockWebhookService` falls back to the SNS envelope's own `Type` if the payload isn't parseable JSON with a `type` field, rather than assuming a shape. A Clock connection is assumed to be enabled on exactly one property (a webhook event with 0 or >1 enabled properties is acked but dropped, logged as a warning) — same class of "basic milestone" simplification as Task 10's single-rate-plan assumption.
- **Task 8**: The exact `/rates_availability` request shape (`rates` + `room_types`/`rooms`) came from Clock's own public Postman workspace ("Clock PMS+ API Docs", organization "Clock PMS+ Integrations", found via Postman's public network search) — the source brief itself left this open (section 38). Blind sandbox probing alone (bare `rates=`, bracket `rates[]=`, POST body) never got past a generic root-level `filled?` validation error; the official docs revealed that `room_types` (or `rooms`) is *also* required alongside `rates`, which the brief's own validation-error body didn't name explicitly. Also newly confirmed via the official docs' example URL: the `pms_api` path is `/{{subscription_id}}/{{account_id}}/...`, i.e. the first path segment is Clock's subscription id and the second is the account id — the reverse of the working-assumption labels in `ClockHttpClient`'s `accountId`/`subscriptionId` fields (Task 4). This doesn't affect correctness (the client just concatenates both positionally) but the field names in code are now known to be swapped relative to Clock's own terminology; not worth a breaking rename mid-milestone, noted here for the Task 15 architecture doc.
