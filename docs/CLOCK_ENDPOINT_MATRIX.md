## Notes

- **Task 3 (2026-08-17):** `ClockBookingConsistencyService` uses the documented read-only `GET /bookings/` date filters `arrival.lt=<endsOn>` and `departure.gt=<startsOn>` for a 31-day-or-less, on-demand stay-overlap check. The list response is a bare numeric-ID array — **confirmed against Empire Beach Resort production** (`[36570822, 36570775, 37779267]`) — so it follows every ID with `GET /bookings/{id}` and reads `id`, `status`, and `reference_number` only from those detail responses. The circuit breaker and rate limiter run for the list and every detail read; rate-limited safe GETs wait before retrying. Findings go through the operational alert channel and are never auto-corrected. A Clock-only record is flagged only when its reference is corroborated by a tenant/property-scoped MUST `integration_operations` record, because this phase deliberately does not import external-channel Clock reservations. The endpoint/filter contract is **CONFIRMED_BY_DOCS** (Clock public Postman API docs); the corrected check requires a final live Empire Beach Resort execution.

(Chronological by the task that discovered them — see `docs/roadmap/milestones/11-clock-pms-adapter-basic.md` for full task context.)

- **Kickoff / Task 4**: The account/subscription ID pair in the URL path (`172528`/`16307` for this sandbox) — which one is the "Clock account ID" vs. "subscription ID" per source brief section 8's terminology was not disambiguated at the time. `room_types` and `rooms` were confirmed reachable and correctly shaped with **real data already present in the sandbox account** (e.g. room type "Standard Rooms", room "Direct Pool") — not empty-state guesses.
- **Task 6**: `ClockPmsProvider.testConnection` and the tenant-facing "Test connection" button both run the full stack for real — HTTP client, rate limiter, circuit breaker, error classification — against the real sandbox, not just the raw Digest probe done at kickoff. Confirmed: a valid connection succeeds end-to-end, and an invalid API key produces a clean, correctly-classified failure rather than a crash or a false success. Clock's 401-on-bad-credentials body is **plain text** (`HTTP Digest: Access denied.`), not JSON — `classifyClockHttpResponse` handles both shapes.
- **Task 8**: The exact `/rates_availability` request shape (`rates` + `room_types`/`rooms`) came from Clock's own public Postman workspace ("Clock PMS+ API Docs", organization "Clock PMS+ Integrations", found via Postman's public network search) — the source brief itself left this open (section 38). Blind sandbox probing alone (bare `rates=`, bracket `rates[]=`, POST body) never got past a generic root-level `filled?` validation error; the official docs revealed that `room_types` (or `rooms`) is *also* required alongside `rates`, which the brief's own validation-error body didn't name explicitly. Also newly confirmed via the official docs' example URL: the `pms_api` path is `/{{subscription_id}}/{{account_id}}/...`, i.e. the first path segment is Clock's subscription id and the second is the account id — the reverse of the working-assumption labels in `ClockHttpClient`'s `accountId`/`subscriptionId` fields (Task 4). This doesn't affect correctness (the client just concatenates both positionally) but the field names in code are now known to be swapped relative to Clock's own terminology — resolves the kickoff/Task 4 note above; not worth a breaking rename mid-milestone, carried into the Task 15 architecture doc instead.
- **Task 11**: No real Clock Message Channels (SNS) subscription exists for this account — configuring one requires Clock account-dashboard access outside this session's reach, so genuinely AWS-signed live traffic could not be captured. What *was* verified for real: the full webhook HTTP flow (routing, RLS-carve-out lookup by `webhookPublicId` across both `integration_connections` and `property_integration_connections`, dedup, BullMQ enqueue) end-to-end using a real, locally-generated RSA key pair to produce genuinely valid SNS-shaped signatures, with only the literal "fetch cert bytes from AWS" network call stubbed (the SSRF-protecting hostname check itself still runs unstubbed and was tested against both real and fake AWS host patterns). Clock's own event payload shape (the JSON string inside SNS's `Message` field) is unconfirmed — the source brief doesn't specify it and no live event has ever been captured, so `ClockWebhookService` falls back to the SNS envelope's own `Type` if the payload isn't parseable JSON with a `type` field, rather than assuming a shape. A Clock connection is assumed to be enabled on exactly one property (a webhook event with 0 or >1 enabled properties is acked but dropped, logged as a warning) — same class of "basic milestone" simplification as Task 10's single-rate-plan assumption.
- **Task 12**: Not a Clock endpoint — MUST's own `manual_review_items` table (source brief section 26). Two of the brief's 7 categories have real trigger code in this milestone (`UNKNOWN_RESULT` from Task 10's timeout reconciliation, `SCHEMA_MISMATCH` from a new response-shape guard on the booking-create success path); the rest are schema-ready only, pending features (payment sync, full reconciliation, Clock-status mapping) that are out of this milestone's scope.
- **Task 14 (this review pass)**: No `ASSUMPTION`-only row is presented as production-ready — the two fully-`ASSUMPTION` rows (Find booking by reference, Guest search) are explicitly flagged as such above, per section 39's own rule. Everything else that shipped in this milestone (auth, catalog list, availability, booking create/update/cancel, the webhook gateway's own endpoint) has at least one `CONFIRMED_*` status backing the code path actually exercised.
- **Post-close-out fix (2026-08-05)**: Every booking-creation attempt through Task 16 had been rejected by Clock with a message naming a missing user right ("Booking: Rate Availability Control Override"), which read as an account-side limitation and was reported to Clock support as such. Clock support pushed back, correctly: granting that right defeats the purpose of `rates_availability`/`products` and is dangerous (bypasses overbooking/restriction checks). Re-investigating from Clock's own public API docs revealed the real cause — this codebase's `ratePlanIds`/`singleRatePlanId` methods fetched `/rate_plans` (a parent grouping id, e.g. `69242`) and used it directly as the `rates`/`rate_id` parameter for `/rates_availability` and `POST /bookings/`, but those endpoints require the room-type-scoped child *Rate* id from `/rates/` (e.g. `784160` for DBL) — Clock's own docs: "1 Rate belongs to 1 Room Type." Fixed in `ClockAvailabilityService.ratesForRoomType` and `ClockBookingService.rateIdForRoomType`, both now querying `/rates/` and filtering by `bookable_type`/`bookable_id`. No override right was ever needed or granted. See docs/CLOCK_SANDBOX_VALIDATION_REPORT.md for the full account of the real success this unblocked.
