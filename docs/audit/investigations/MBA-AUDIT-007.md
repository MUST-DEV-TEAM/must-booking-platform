## Adjudication

**MBA-012: VERIFIED FINDING, HIGH/NOW for local false completion.** PokPay's successful refund response is `REFUNDED` only when `sdkOrder.isRefunded` is true; otherwise it is `REFUND_PENDING` (`P:104-127`). Stripe passes `refund.status ?? 'succeeded'` through without requiring success (`S:180-195`). `R:175-187` checks only `Result.ok`, ignores `value.status`, and inserts `payments.status='REFUNDED'` for either provider. For a newly inserted row, it records `payment.refunded` and `PAYMENT_REFUNDED`, prepares guest confirmation and a Clock mirror candidate (`R:193-246`). This is a submitted/accepted provider request being represented locally as settled; actual payout and later failure frequency require provider evidence. The successful `Result<Payment>` with `value.status='REFUND_PENDING'` (or Stripe `pending`, `requires_action`, `failed`, `canceled`, or any other returned string) is the ignored payload. Even Stripe's null status is converted to `succeeded` by the provider. The service returns the provider's own status to the API (`R:243-246`, `R:319-320`, controller `apps/api/src/payments/payment-refund.controller.ts:36-48`), which is counterevidence to claiming the returned value itself is forcibly changed to `REFUNDED`.

**Effects differ by path.** Manual gateway refunds call `refundCharge`, then Clock `postRefund` inside the same transaction when a new refund row was inserted (`R:250-319`, `R:403-451`). The Clock path can post a negative credit item and a manual-review item (`C:915-1035`), so a pending provider response can trigger Clock mirroring. A guest email is sent after commit only if the booking/guest query yields a confirmation (`R:215-239`, `R:319`); in-app notification is written on insertion. Automatic single and group cancellation call the same `refundCharge` (`L:1069-1079`, `L:1247-1267`) and send any collected confirmations after the cancellation transaction (`L:1133-1137`); `R:53-59` and those callers deliberately do not use `clockRefund`. Late-expiry Stripe webhook refund also calls `refundCharge` and sends a confirmation after its transaction (`apps/api/src/payments/stripe-webhook.service.ts:73-113,150-164`). Cancellation notification independently selects `payments.status='REFUNDED'` (`apps/api/src/mail/booking-cancellation-notification.service.ts:70-87`), so the premature row affects that message too.

**Provider refusal versus uncertainty.** A provider `Result.ok=false` causes no refund row, refunded audit/in-app notification, email confirmation or Clock mirror (`R:180`). In automatic cancellation it creates a manual-review failure and cancellation continues (`L:1077-1078`; group `L:1262-1267`); late-expiry Stripe processing throws (`apps/api/src/payments/stripe-webhook.service.ts:110`). PokPay non-2xx, malformed response and thrown transport errors become `Result.ok=false`, with 5xx/transport marked retryable (`P:205-241`); `STRIPE_REFUND_FAILED` catches all Stripe exceptions as retryable (`S:171-199`). A timed-out/failed transport is **unknown external outcome**, not proof of provider refusal. PokPay's missing order ID after successful HTTP response is also a local failure (`P:115-118`) with external outcome not established. A provider `Result.ok=true` carrying a failed status is instead falsely marked completed by the service. The offline probe below verifies the pending/explicit refusal branches in the real service method with fake dependencies; it does not simulate an actual provider or SQL commit.

**No refund settlement repair was found in the inspected handlers: VERIFIED SOURCE SCOPE; production behavior NEEDS VERIFICATION.** Stripe webhook verification passes non-checkout events through, but the controller processes only paid checkout session events (`S:128-136`; `apps/api/src/payments/stripe-webhook.controller.ts:39-53`). PokPay's authenticated order reread and pending-order poll handle charge sessions and paid booking continuation (`apps/api/src/payments/pokpay-payment.service.ts:29-145`); `P:130-148` can expose order refund status, but that service does not apply it to refund rows. `payment-expiry.service.ts` has no refund branch. This supports absence of a refund-completion/failure transition in the named paths, not a claim about every external process or deployed integration.

**MBA-016: VERIFIED FINDING, HIGH/NOW for source transaction/transport boundary; duplicate money movement NEEDS VERIFICATION.** Manual refund opens `withTenantTransaction` then creates an `integration_operations` PENDING row and calls the external provider before updating the result, all inside that transaction (`R:257-318`, `R:497-547`). `T:27-43` supplies the Prisma interactive transaction; manual refund passes no timeout override, so it uses the client's default transaction budget. The service extends `PrismaClient` without supplying constructor options (`T:18`), and no `transactionOptions` override was found in the inspected API source. Its comment calls Prisma's default 5,000 ms (`T:37-41`), but no live effective timeout was measured. It also holds the booking `FOR UPDATE` lock across the call (`R:259`, `R:484-495`). `R:313-315` calls Clock before commit, including outbound work in `C:925-1035`. The catch in `R:420-449` tries to record review through the same `tx`; if SQL has already expired/aborted, it cannot establish durable recovery. `integration_operations` PENDING, final result, ledger and review writes in that manual call are not committed ahead of the external call; an abort leaves no durable manual refund intent from this transaction. A commit response lost after commit is a separate ambiguity: the row may exist and the same idempotency key can return its stored result (`R:516-546`). Automatic cancellation is also external inside its 30-second transaction (`L:998-1014,1069-1079,1130-1133`) and group uses the same transaction (`L:1145-1149,1253-1267`); late-expiry Stripe refund is inside a 45-second transaction (`apps/api/src/payments/stripe-webhook.service.ts:50-53,95-110,150-155`). This narrows MBA-016's former manual-only wording.

Stripe submits `command.idempotencyKey` to `stripe.refunds.create` (`S:180-186`), giving its replay a provider-side key even if the SQL transaction aborts. Its remote guarantee and retention window were not verified here. PokPay's refund POST body contains only amount/reason, and `authenticatedRequest` builds only bearer/content-type headers with no `command.idempotencyKey` (`P:104-114,205-218`). It supplies no explicit abort signal/deadline (`P:214-219`, authentication `P:244-250`), although the runtime/network may impose limits outside this source. PokPay's remote deduplication or refund lookup contract is **NEEDS VERIFICATION**; do not claim duplicates are inevitable. A retry after an aborted SQL transaction can resubmit the request because the operation insert rolled back, while the provider outcome is unknown. `payments` has a tenant/external-ID uniqueness constraint (`apps/api/prisma/schema.prisma:615-634`), which prevents duplicate local rows with an identical ID but cannot prove the provider did not create a second refund with a different ID. This links to MBA-001's rollback pattern and MBA-013's connection-identity risk without reauditing either.

**Recommended narrow record/behavior change (RECOMMENDATION, not implementation):** make submitted/pending, confirmed success, explicit failure and unknown outcome distinct; persist a tenant/property-scoped refund attempt and provider request key before outbound work, then reconcile unknown outcomes before replay. Gate `REFUNDED` ledger semantics, completion mail, in-app completion and Clock negative payment on an authoritative success appropriate to each provider. Keep refusal distinct from timeout. Preserve Stripe's idempotency key and verify PokPay's documented idempotency/query capabilities before designing its replay. Move Clock effects after the local refund commit with durable retry/review. ADR-0018 requires free-cancellation automatic refund and idempotency, but does not define provider settlement timing; that business decision needs owner acceptance before product changes.
