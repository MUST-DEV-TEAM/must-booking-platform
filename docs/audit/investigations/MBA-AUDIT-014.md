## MBA-100 — Suspension state versus admitted operations

**VERIFIED FINDING for the checked-in control gap; retain HIGH / NOW only if suspension is intended to stop staff or guest operations. QUESTION for the exact suspension policy.** Platform-only `POST /platform/tenants/:tenantId/suspend` reaches `transitionTenant`, which conditionally updates `organizations.status` from ACTIVE to SUSPENDED and audits the change in the same tenant transaction (`apps/api/src/platform/platform-admin.controller.ts:10-12,72-79`; `apps/api/src/platform/platform-admin.service.ts:270-281,309-339`). Its compare-and-update predicate guards concurrent transitions; the action is not a no-op. The enum/column exist (`apps/api/prisma/schema.prisma:69-82`).

The staff `TenantContextGuard` validates session, tenant membership and optional property existence, without reading organization status (`apps/api/src/tenancy/tenant-context.guard.ts:64-98`). `RolesGuard` checks membership roles/property assignment, not status (`apps/api/src/tenancy/roles.guard.ts:47-79`); capability evaluation likewise checks membership/assignment (`apps/api/src/tenancy/capabilities.service.ts:7-27`). An existing or freshly logged-in eligible member can therefore pass these application gates after suspension, subject to the route's ordinary roles/capabilities. The public `PublicTenantScopedGuard` checks tenant/property parameters and property existence, then binds a staff or anonymous guest session; it also omits status (`apps/api/src/tenancy/public-tenant-scoped.guard.ts:31-88`). A concrete guest booking mutation is still routed through that guard (`apps/api/src/booking/booking.controller.ts:61-75`). The public booking route also has its own rate limiter and booking/quote checks, so guard admission alone does not prove that every booking succeeds. Search of `apps/api/src/auth`, `tenancy` and `booking` found no ACTIVE/SUSPENDED predicate; only platform administration references organization status. Historical platform tests establish transition/audit behavior, not a suspension admission boundary (`docs/roadmap/completed/08-platform-admin-dashboard.md`, Tasks 3 and 12).

Accepted ADR-0021 authorizes the suspend/reactivate action but does not define which requests, payment recovery, workers or webhooks it should block (`docs/decisions/ADR-0021-platform-admin-cross-tenant-data-access.md:12-26`). Hence the source verifies that status is currently an administrative marker rather than an enforced admission check; whether every cited operation *must* stop is an owner policy question. Proposed MBA-100 edit: replace the universal “retains staff access and accepts guest bookings” consequence with “staff and public booking entry gates do not consult SUSPENDED; eligible requests can proceed to ordinary downstream checks.” Define allowed/blocked operations before remedy, especially refunds, provider callbacks and reconciliation. **NEEDS VERIFICATION:** deployed schema/runtime and end-to-end suspended-tenant behavior; no production containment claim follows from this source review.

## MBA-103 — Property entry gate, tenant-wide duplicate mutation

**VERIFIED FINDING for scope mismatch; HIGH / BEFORE PILOT is reasonable, with authorization policy unresolved.** Guest list, duplicate review, dismissal and merge all use a property URL and accept OWNER/ADMIN or PropertyStaff with `guests.manage`; the two writes require verified email (`apps/api/src/tenancy/guests.controller.ts:9-75`). A STAFF caller must already have a tenant membership, property assignment and effective capability for the URL property (`apps/api/src/tenancy/tenant-context.guard.ts:77-98`; `apps/api/src/tenancy/roles.guard.ts:57-79`; `apps/api/src/tenancy/capabilities.service.ts:18-26`; `apps/api/src/auth/email-verification.guard.ts:20-32`). This is a real restriction, not anonymous access.

The ordinary directory query stays at that property by joining bookings on `b.property_id` and counting only those bookings (`apps/api/src/tenancy/guests.service.ts:51-86`). The suspected-duplicate list instead enters a transaction with only `{ tenantId }`, exposes both profiles and each *tenant-wide* booking count, and requires a booking at the requested property for **either** member of the pair (`:89-164`). Thus a pair involving one local profile can reveal the other profile's name/email/phone and total booking count even if that other profile's bookings are elsewhere. Dismissal takes any valid flagged same-tenant guest ID and clears its advisory pointer without checking that either profile has a booking at the URL property (`:167-193`). Merge also enters `{ tenantId }`, locks the same-tenant flagged/pair rows, and reassigns every booking of the losing guest in the tenant, with no `property_id` predicate (`:196-250`). It backfills/tombstones the tenant-wide profiles (`:253-305`). The flags and tombstone references are constrained to the same tenant (`apps/api/prisma/migrations/20260910100000_guest_suspected_duplicate/migration.sql:16-21`; `20260910110000_guest_merge_tombstone/migration.sql:16-21`). TenantDatabaseService uses transaction-local tenant/property settings (`apps/api/src/tenancy/tenant-database.service.ts:19-35`); guest RLS is tenant-only (`apps/api/prisma/migrations/20260730060000_guests/migration.sql:20-25`), and booking RLS allows all tenant properties when property context is absent (`apps/api/prisma/migrations/20260730010000_bookings_state_machine/migration.sql:64-73`). This is **within-tenant** authority expansion, not a cross-tenant RLS bypass.

The shared Guest model is explicitly tenant-wide (`docs/architecture/data-and-access.md`, “Model and scope”), and ADR-0030 intentionally moves *all* losing-guest references in a manual merge. A property-filtered booking update would split one identity incorrectly. What remains unsettled is **who** may approve a tenant-wide merge/dismiss and how much of another property's profile a local reviewer may see. Proposed MBA-103 edit: state the unqualified dismissal path separately from pair-list disclosure and global merge; present “unauthorized across properties” as a **LIKELY FINDING pending explicit tenant-wide guest-management policy**, while retaining the verified scope mismatch. Recommend an explicit tenant-wide permission/owner-admin decision or a carefully defined delegated review rule; test a STAFF user assigned only to property A against a pair/flag confined to property B and a pair spanning A/B. A valid same-tenant flagged ID is a precondition for direct dismissal; the normal review list supplies IDs only when at least one pair member has a local booking. **NEEDS VERIFICATION:** actual multi-property RLS/SQL behavior and approved reviewer policy.

## MBA-104 — Canonical choice and Clock mapping preservation

**VERIFIED FINDING for two source defects; retain HIGH / BEFORE PILOT with conditional downstream impact.** The controller accepts `canonicalGuestId` as the staff choice (`apps/api/src/tenancy/guests.controller.ts:59-75`). ADR-0030 decision 4 and Milestone 21 Phase B explicitly allow either candidate as canonical (`docs/decisions/ADR-0030-guest-matching-phone-signal-and-merge.md`, “Manual merge”; `docs/roadmap/milestones/21-clock-certification-fixes.md:43-48`). `GuestsService.mergeSuspectedDuplicate` rejects `flaggedGuestId === canonicalGuestId` *before* its transaction (`apps/api/src/tenancy/guests.service.ts:203-208`), yet later branches explicitly handle `canonicalId === flaggedGuestId` (`:233-240`). The flagged profile therefore cannot be selected as canonical through this method. It still checks that a different requested canonical ID equals the current candidate, that both are active, and that the pair belongs to the same tenant (`:209-243`); arbitrary other guest IDs are not accepted.

The merge updates bookings, guest fields/pointers and audit data but has no `clock_guest_mappings` update (`apps/api/src/tenancy/guests.service.ts:245-305`). That mapping has a same-tenant guest FK, unique `(tenant_id, property_id, guest_id)` and unique `(tenant_id, property_id, external_guest_id)` (`apps/api/prisma/migrations/20260911100000_clock_guest_mappings/migration.sql:3-23`). Because the losing guest remains a tombstone rather than being deleted, its FK-bound mapping also remains. Clock booking lookup asks for the mapping by the **canonical** guest ID (`apps/api/src/integrations/clock/clock-booking.service.ts:1570-1582`), so a prior mapping belonging only to the losing ID is not found. Later code may fall back to Clock email search (`:292-315`); if it finds that same external ID, `rememberClockGuest` uses `ON CONFLICT DO NOTHING` (`:1585-1599`), so the unique external-ID claim held by the tombstone prevents persistence under the canonical ID. That supports a repeated lookup/stale identity risk, not a demonstrated wrong external booking or provider conflict response. Where both profiles have mappings for one property, reassignment needs an explicit conflict policy. The data/access document's sentence saying merge moves Clock mappings overstates the current code (`docs/architecture/data-and-access.md`, “Guests, staff and integration credentials”).

The existing isolated fake-transaction unit test covers candidate-as-canonical and dismiss, not flagged-as-canonical, property authority or mapping migration (`apps/api/src/tenancy/guests.service.spec.ts`). A full migrated database, actual mapping collision behavior and live Clock outcome remain **NEEDS VERIFICATION**. Recommend allowing either valid candidate, and reconciling property-scoped mappings in the same locked merge with explicit conflicting-external-identity handling. Keep MBA-103's authorization decision separate from this data-integrity fix.
