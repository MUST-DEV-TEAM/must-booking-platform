## Safeguards and limits

The `bookings`, `guests`, `integration_operations`, `availability_blocks` and target tables, override table and `audit_logs` migrations enable and FORCE RLS and define tenant-scoped `USING`/`WITH CHECK` policies (`20260730010000_bookings_state_machine/migration.sql:62-73`; `20260730060000_guests/migration.sql:20-25`; `20260730050000_integration_operations/migration.sql:26-37`; `20260803160000_manual_availability_blocks/migration.sql:49-87`; `20260727213000_property_staff_capability_overrides/migration.sql:19-24`; `20260728000000_audit_logs/migration.sql:20-37`). The repair drops FKs, not RLS or policies. These policies check fields **on each row**; their SQL contains no referenced-ID membership test. Thus the absent FKs remove a database referential backstop while RLS still gates ordinary row access. Property context can be absent, intentionally allowing tenant-wide rows where policies permit. The audit-log policy also allows global `tenant_id IS NULL` inserts, and a later platform-admin policy grants SELECT-only cross-tenant log reads (`20260802130000_platform_dashboard_read_carve_out/migration.sql:1-10`).

`TenantDatabaseService.withTenantTransaction` sets transaction-local tenant/property context (`apps/api/src/tenancy/tenant-database.service.ts:19-35`). The runtime-role migration declares `must_booking_app` `NOSUPERUSER NOBYPASSRLS` and grants table DML (`20260727180000_runtime_database_role_and_users_insert_policy/migration.sql:1-35`). The SQL declares FORCE RLS, but source declarations cannot certify deployed privileges, actual app connection role, migration application, or security-definer paths. A privileged maintenance connection may have different RLS treatment. No current cross-tenant request or successful invalid write was reproduced.

Prisma models encode the booking `guestId`, guest `tenantId`, operation `propertyId`, block/target IDs, and override `userId`/`capabilityId` as scalar fields without the missing relations (`apps/api/prisma/schema.prisma:262-274,390-423,528-582,653-677,700-717`). The scalar form explains why generated schema diffs may not recover these SQL-owned constraints, but SQL-maintained room images show that scalar-only modeling can be a deliberate choice. The booking still has composite property/catalog relations (`schema.prisma:561-564`); later guest self-FKs and Clock mapping FK are additional protections, not restoration of its guest FK. AuditLog's nullable tenant field is scalar-only (`schema.prisma:277-291`).

Representative paths temper impact. Block creation checks requested room and room-type IDs under a tenant/property transaction, then writes scoped rows (`apps/api/src/tenancy/availability.service.ts:342-386`). Its scoped block deletion does not delete target rows explicitly (`:411-433`), so the lost block-target CASCADE can leave orphaned target rows if a block with targets is deleted in a migrated database. Capability evaluation joins overrides through assignment and capability (`apps/api/src/tenancy/capabilities.service.ts:18-25`); an orphan override would not by itself grant an effective capability through this query. Those examples do not establish a reachable malicious endpoint or a cross-tenant disclosure.

## Proposed MBA-106 edits and verification

Keep a **VERIFIED FINDING for bounded migration-source evidence** concerning eleven unrestored constraints, with **deployed state and invalid-row outcomes UNVERIFIED**. Change the title to “Schema repair leaves eleven foreign keys unrestored in the migration chain.” State that RLS persists and gates row tenant/property fields; missing composite FKs no longer force referenced IDs to belong to the same scope or exist. Replace universal “lost cascade cleanup” with the block-target and guest/audit-log families only, subject to retention policy. Remove an implied current cross-tenant exploit and describe invalid links as possible after a faulty or privileged write. Separate audit-log organization-delete behavior as a retention choice. Keep BEFORE PILOT remediation; rate current supported severity **MEDIUM integrity/defense-in-depth, high source confidence**, with HIGH conditional on migrated-database evidence of affected data or a reachable write path. Do not treat renamed booking FKs, recreated payment FKs, or the restored room-image FK as losses.

Before a product change, inventory `pg_constraint` on a disposable database migrated from the complete chain under the intended migration role; inspect `pg_class.relrowsecurity`/`relforcerowsecurity`, `pg_policies`, roles and grants. Preflight orphan and mismatched-scope rows per missing link, decide audit-log retention, then add deliberate composite constraints with validation and a rollback plan. Test scoped insertion/deletion using the intended non-bypass app role and separate privileged maintenance role. No such database check was authorized or run here.
