## Verdict and evidence

**VERIFIED FINDING (source/control flow):** The single-booking `ok: false` Clock attachment path rolls back the local receipt and its failure evidence. `StripeWebhookService.processPaymentSucceeded` inserts a `PAID` charge and then calls `continueAfterPayment` in the same `withTenantTransaction` callback (`apps/api/src/payments/stripe-webhook.service.ts:50-52,128-154`). A false continuation result is converted to a thrown `StripeWebhookProcessingError` at line 142. `TenantDatabaseService.withTenantTransaction` returns Prisma's interactive `$transaction` around that callback (`apps/api/src/tenancy/tenant-database.service.ts:19-43`); an escaping exception aborts the transaction. The controller has no catch that could commit the aborted work (`apps/api/src/payments/stripe-webhook.controller.ts:49-59`). This is a transaction-semantics conclusion, not a database reproduction.

`LocalPmsProvider.continueAfterPayment` first transitions `PAYMENT_PENDING` to `PMS_CREATION_PENDING`, then returns `attachRealReservation`'s result for a single Clock booking (`apps/api/src/booking/local-pms.provider.ts:790-853`). The adapter's explicit failure branches include missing connection/guest/mapping, rate or guest lookup failure, create POST failure (including unresolved timeout/network response), malformed 2xx create response, and failed local reload (`apps/api/src/integrations/clock/clock-booking.service.ts:472-565,577-590,619-677,707-715`). They write `PMS_UNKNOWN_RESULT` where specified and/or `ManualReviewItem` inside the supplied `tx` (`:643-652,655-677`; `recordPostCommitFailure` at `:1721-1748`). Despite that helper's name and comment, it does not open a separate transaction. The webhook's throw therefore erases these writes along with the charge and `PMS_CREATION_PENDING` transition. The pre-existing booking remains `PAYMENT_PENDING`; the external Stripe capture is unaffected by SQL rollback.

**Counterevidence / limits:** This does **not** happen for every Clock failure. In a multi-room order, `continueMultiRoomOrderAfterPayment` skips a failed child, returns a successful anchor result, and permits the charge and child's unknown-result/review writes to commit (`apps/api/src/booking/local-pms.provider.ts:870-930`). `apps/api/test/multi-room-booking.e2e.spec.ts:613-658` asserts precisely that outcome with a stubbed second-room failure. For a single booking, failure to post a deposit is returned by `postDeposit` but its result is ignored by continuation after successful attachment (`apps/api/src/booking/local-pms.provider.ts:836-853`; `apps/api/src/integrations/clock/clock-booking.service.ts:779-805,836-875`), so its review can commit. A timeout/network create failure that successfully links by reference also returns success (`clock-booking.service.ts:625-635,1493-1529`). Local-only fulfillment succeeds without Clock (`local-pms.provider.ts:855-867`). An unexpected exception or transaction timeout can still abort even after an external success; this separate commit-ambiguity case needs a controlled test.

**LIKELY FINDING (consequence):** A retried callback for the same paid event sees the booking as `PAYMENT_PENDING` and no committed `payments.external_payment_id`, so the SQL deduplication at `stripe-webhook.service.ts:128-139` does not stop another continuation. `attachRealReservation` checks a **committed local** `external_booking_id` at `clock-booking.service.ts:491`; its reference lookup occurs only *after a timeout/network POST failure* (`:619-635,1493-1529`), not before a new POST. Thus a retry may issue another create if the first POST created a reservation but its local writes rolled back. Whether Clock itself rejects duplicate `reference_number`, or a specific retry actually creates a second reservation, is **NEEDS VERIFICATION**. No duplicate was reproduced or observed. Failure before the create POST cannot itself have created a Clock reservation.

**LIKELY FINDING (operational consequence):** A rolled-back paid single booking is eligible for the existing `PAYMENT_PENDING` expiry path (`apps/api/src/booking/local-pms.provider.ts:933-985`; `apps/api/src/payments/payment-expiry.service.ts:65-81`). Expiry is conditional on age and sweep execution; it is not an immediate or inevitable consequence. The separate `EXPIRED` webhook branch records a late charge and attempts refund (`stripe-webhook.service.ts:73-113`), but it does not restore the lost initial fulfillment history.

## MBA-001 correction recommended to Astra

Retain **CRITICAL as a pre-live architectural severity** and **NOW as a repair gate before real-money use**, subject to Astra's acceptance. The coordinating audit reports current Stripe key enforcement is test-mode only; this bounded unit did not inspect that enforcement or establish current production exposure to real captured money. Narrow the title/current behavior to **“Single-booking Stripe webhook rolls back payment and Clock failure evidence when attachment returns failure.”** Replace “a callback retry can repeat the external create” with “a retry can re-enter attachment and issue another POST after a prior ambiguous create; actual duplicate reservation depends on Clock behavior and has not been reproduced.” State explicitly that group child failures and deposit posting failures have different commit behavior. Keep the adverse duplicate outcome labeled risk, not verified impact.

Safe follow-up: add a no-network test using a known isolated test database or transactional stub that forces a single-booking `attachRealReservation` to write unknown-result/manual-review then return `ok: false`; assert the webhook rejects, no charge/review/status transition commits, and a second delivery re-enters attachment. Separately model a POST that succeeds externally before a local failure to test reference recovery and any Clock-enforced uniqueness with an approved sandbox only. The repair should commit the authenticated charge independently of fulfillment, persist a durable attempt/review state, and gate a new create on reconciliation by MUST reference. Do not infer that a failed payment callback means the gateway did not capture funds.
