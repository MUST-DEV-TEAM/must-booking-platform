# MBA-AUDIT-013 — Auth recovery and staff invitation challenge

**Astra disposition (2026-09-27): COMPLETE.** Accepted narrowed HIGH source findings MBA-101/102/107. Credited signup limits, generic responses, token entropy/expiry/single-token replay protection, invitation creator/session guards, seat/role/uniqueness constraints and unverified deployed controls. False verification of an unused email and recipient substitution are distinct from existing-account or mailbox takeover. Source tracing is not runtime exploitation; no product correction was implemented.

Status: COMPLETE for bounded source adjudication, 2026-09-27. Owner-authorized audit documentation outside the active milestone table. Bounded repository source review only. No product changes, real accounts, provider calls, database or Redis access, or application boot.

## Evidence preserved so far

- **MBA-101 — VERIFIED FINDING (application layer):** `apps/api/src/auth/auth.controller.ts:28-84` applies `@SignupRateLimited` only to signup; login, password-reset request/confirm and email-verification request/confirm have no matching decorator. `apps/api/src/auth/signup-rate-limit.guard.ts:27-32` explicitly passes handlers without that metadata. `apps/api/src/app.module.ts:284-289` registers this guard globally, alongside context, role, capability and verification guards, with no general auth throttler there. `apps/api/src/tenancy/public-rate-limit.guard.ts` is used on selected public domain handlers, not these auth routes. This supports missing checked-in application throttles on the listed auth handlers. Deployed edge controls remain unknown; do not claim WAF absence. Generic request responses exist (`auth.controller.ts:71-82`), while `auth.service.ts:247-285` issues and mails tokens for eligible accounts. No conclusion about actual delivered email volume or credential stuffing incidents.
- **MBA-102 — VERIFIED FINDING (source lifecycle):** `apps/api/src/auth/auth.service.ts:324-332` creates independent 32-byte random, hashed-key reset/verification tokens with 3600/86400-second TTLs. `:423-429` consumes one matching key via Redis `GETDEL`; `:262-268` then updates the password in PostgreSQL. `:353-360` stores each UUID session for 604800 seconds containing only `userId`; `:199-227` reads it and looks up the current user without password-generation comparison. `:186-196` deletes only the presented logout session. There is no reset-time session or sibling-token invalidation in these paths. Token replay after successful `GETDEL` is blocked, but a sibling token remains usable within its TTL. Redis token consumption precedes the database write, so database failure burns the token; no cross-resource atomicity. Runtime Redis/DB behavior untested.
- **MBA-107 — VERIFIED FINDING (source identity binding), consequence to narrow:** `apps/api/src/tenancy/staff-invite.controller.ts:18-32` gates creation on tenant owner/admin role, `staff.invite` capability and verified email, then returns the token to the creator. Public activation accepts separate token/email/password at `:35-42`; existing-user acceptance needs a valid session at `:44-57`. `apps/api/src/tenancy/staff-invite.service.ts:66-79` stores a 32-byte random token under a SHA-256 Redis key for 604800 seconds, emails the invite target and returns the token. `:82-109` consumes the token before transaction, but neither activation nor acceptance compares the target email to the submitted/new or session user's email. `:239-250` inserts the supplied activation email with `email_verified_at = CURRENT_TIMESTAMP`. This permits an authorized invite creator who has the token to assert verification for an unregistered third-party email, subject to seat/role/database constraints. This is account squatting/false mailbox verification, not demonstrated access to an existing user's account or mailbox.

Existing `apps/api/test/auth.e2e.spec.ts` and `staff-invite.e2e.spec.ts` create local PostgreSQL/Redis state and boot AppModule, so they are excluded under this unit's constraints. The focused signup-guard test does not exercise the disputed routes. No behavioral tests ran.

## Adjudication and counterevidence

**MBA-101 — retain HIGH / BEFORE PILOT, narrowly.** Login (`auth.controller.ts:46-58`), reset request/confirm (`:71-77`) and verification request/confirm (`:78-85`) lack handler throttle metadata or service-local limiter calls. The global `SignupRateLimitGuard` is wired at `apps/api/src/app.module.ts:284-289`, but explicitly passes handlers without its decorator (`apps/api/src/auth/signup-rate-limit.guard.ts:27-32`). `PublicRateLimitGuard` is only provided there, not globally registered, and itself passes undecorated handlers (`apps/api/src/tenancy/public-rate-limit.guard.ts:28-35`). Other global guards handle context, roles, capabilities and verified email, not request frequency. Signup *does* have an application Redis limit of 10/IP and 3/email per hour (`apps/api/src/auth/signup-rate-limiter.service.ts:5-7,20-27`), so the original claim must not imply all auth endpoints lack controls. `auth.service.ts:159-168` runs bcrypt comparison for a found account; passwords shorter than 12 are rejected before that step (`:439-444`). Reset requests issue and attempt email for known users (`:247-260`); verification requests do so only for unverified users (`:270-285`). Controller request responses are generic (`auth.controller.ts:71-82`); mail failures are logged but swallowed (`auth.service.ts:388-412`). These are application workload and mail-attempt paths, not proof of delivered-email flooding, credential compromise or absent deployed WAF. The current host's edge rules, trusted-client-IP model and actual observed limits are **NEEDS VERIFICATION**: `docs/operations/README.md:3-11` disclaims live verification, and checked-in retired-homelab Cloudflare references do not establish current policy. Proposed edit to MBA-101: say “no checked-in application abuse limiter on login, reset or verification”; separate any MFA/step-up policy from this focused throttle finding. Recommend bounded per-account and trusted-client-IP limits, with deployed edge rules checked separately.

**MBA-102 — retain HIGH / BEFORE PILOT.** The reset token has 32 random bytes, a hashed Redis key and 3,600-second TTL (`auth.service.ts:253-259,324-327`); the email-verification token separately has 32 random bytes and 86,400-second TTL (`:330-333`). Redis `GETDEL` consumes only the presented key atomically (`:423-429`). This blocks replay of that token but does not revoke independently issued siblings. Sessions are random UUID bearer IDs, last 604,800 seconds and store only `{ userId }` (`:353-360`); lookup resolves the current user without comparing an auth generation (`:199-227`). Logout deletes one presented session (`:186-196`). Password reset consumes one Redis token before bcrypt and PostgreSQL `auth_update_password` (`:262-268`); that SQL function only updates `password_hash` and `updated_at` (`apps/api/prisma/migrations/20260727190000_authentication_primitives/migration.sql:18-27`). If the DB/hash step fails, the link has already been burned while the old password remains; if Redis consumption fails, the password update is not reached. A valid prior staff session continues through the tenant guard's membership check (`apps/api/src/tenancy/tenant-context.guard.ts:64-98`) and a platform session through the platform role guard (`apps/api/src/tenancy/roles.guard.ts:36-44`), provided the user/role still exists. This is **VERIFIED FINDING** in source control flow, with deployed Redis/database failures and concurrent confirmations **NEEDS VERIFICATION**. Proposed edit: explicitly credit token entropy, expiry and one-token replay resistance; focus remedy on user-wide session/sibling-token revocation and a defined cross-resource partial-failure path.

**MBA-107 — retain HIGH with narrower impact and reachable preconditions.** Invitation creation is restricted to a session-scoped tenant OWNER/ADMIN with `staff.invite` and verified email (`staff-invite.controller.ts:18-32`; `apps/api/src/tenancy/roles.guard.ts:47-79`; `apps/api/src/tenancy/capabilities.guard.ts:20-34`; `apps/api/src/auth/email-verification.guard.ts:20-32`). The creator receives the token (`staff-invite.controller.ts:23-32`) as well as the intended target receiving an attempted mail (`staff-invite.service.ts:66-79,159-209`); failed mail leaves a valid token. The token has 32 random bytes, a hashed Redis key, 604,800-second TTL and atomic `GETDEL` consumption (`staff-invite.service.ts:66-69,215-220`). It is neither guessable from the email nor normally replayable after consumption.

New-user activation accepts a separately supplied email/password (`staff-invite.controller.ts:35-42`). It validates email shape and 12-character password but never compares the supplied email with the stored invite email (`staff-invite.service.ts:90-109`), then inserts its lowercase form with `email_verified_at = CURRENT_TIMESTAMP` (`:239-250`). Invite creation stores the caller's target email without normalization (`:66-69`); auth login/recovery lowercases incoming email (`auth.service.ts:474-479`) and SQL lookup is case-insensitive (`apps/api/prisma/migrations/20260727190000_authentication_primitives/migration.sql:5-16`). A verified authorized invite creator can therefore use the returned token to create a STAFF account under an *unused* third-party address with a password the creator chose, falsely asserting mailbox verification. This is account squatting and bypass of verified-email gates on later tenant mutations; it is **not** demonstrated access to the mailbox or a takeover of a pre-existing account. The global `users.email` unique index (`apps/api/prisma/schema.prisma:108-119`; `apps/api/prisma/migrations/20260727170000_tenancy_auth_core_schema/migration.sql:27-34`) prevents overwriting an existing exact-email account. Existing-user acceptance requires a valid session (`staff-invite.controller.ts:44-57`) yet never compares that account's email or verified state with the invite target (`staff-invite.service.ts:82-88`): a forwarded/stolen token can substitute another signed-in recipient, subject to seat and assignment constraints. This is not a login bypass.

Both creation and redemption check tenant staff seats, and redemption locks the organization row before count/insert (`staff-invite.service.ts:45-65,82-103,305-344`). Pending invites do not reserve seats; this is the stated Milestone 2 Task 7 tradeoff, while ADR-0007 defines total-roster hard limits (`docs/roadmap/completed/02-signup-and-free-trial-onboarding.md`, Task 7; `docs/decisions/ADR-0007-pricing-model.md:26-28`). Redemption inserts STAFF membership and assigned property roles/capability grants, not OWNER/ADMIN (`staff-invite.service.ts:253-278`), and explicitly rejects platform-admin membership (`:281-290`), consistent with accepted ADR-0020. SQL/RLS constraints still have to accept tenant, property and template IDs; no cross-tenant assignment was demonstrated. Existing-account activation instead reaches unique-email rejection (`:104-109,293-302`), covered by a pre-existing e2e test claim at `apps/api/test/staff-invite.e2e.spec.ts:242-249`, not rerun here. Both redemption methods consume via Redis before the SQL transaction (`staff-invite.service.ts:82-109,215-220`), so seat-cap rejection, duplicate email or downstream SQL failure burns the link without committing access; no Redis/PostgreSQL atomic transaction exists. The existing e2e scenarios at `apps/api/test/staff-invite.e2e.spec.ts:195-249` use matching emails and do not cover mismatch or failure retry. Proposed edit: bind normalized invite target to both new-user and session-user redemption; because the creator can read the token, derive the activation email from the invite alone is insufficient to prove mailbox control. Define mailbox-verification and safe-retry behavior explicitly. The reviewed accepted ADRs settle seat/role constraints but do not specify an exception to target-email binding or an invitation verification UX. Runtime SQL/Redis behavior, deployed token handling and exact driver error translation remain **NEEDS VERIFICATION**.
