## MBA-003: occupancy bound by the quote versus stored on the child

**VERIFIED FINDING (source/control flow; HIGH):** `POST /bookings/orders` forwards `guestCount` for each room but drops submitted `adults` and `children` (`apps/api/src/booking/booking.controller.ts:100-115,215-254`). The group command likewise has only `guestCount` per child (`apps/api/src/booking/multi-room-booking.service.ts:19-38`). Its `QuoteService.validate` expected object omits all three occupancy fields (`multi-room-booking.service.ts:95-106`), so `resolveBookingOccupancy(expected)` becomes one adult, zero children (`apps/api/src/booking/quote.service.ts:329-340`; `apps/api/src/booking/booking-occupancy.ts:17-20`). The subsequent child INSERT separately normalizes the *submitted* `room.guestCount` and stores it as `adults` and `guest_count`, with zero children (`multi-room-booking.service.ts:135-155`). `validateCommand` only requires a supplied `guestCount` to be a positive integer (`:257-273`); it does not bind it to the signed quote.

The saved real `QuoteService` probe in `docs/audit/CHECK_EVIDENCE.md:12-22` is the behavioral counterexample; it was **not rerun** here. With the exact expected-field shape used by the order, one-adult quote validation returned `null`, two-adult quote validation returned `QUOTE_MISMATCH`, and the changed `guestCount: 8` was an annotation showing it was not passed to validation. Thus a valid two-adult quoted child is rejected even if the request supplies `guestCount: 2`; a one-adult quoted child may pass validation with `guestCount: 8` and then reach an INSERT that would store eight adults, subject to later SQL/provider outcomes. The probe does not show an eight-adult row committed. Quote creation normalizes occupancy and signs it (`quote.service.ts:69-93,414-421`), so the defect is the order's expected input and later persistence, not a missing signature. Single-booking validation passes normalized adults/children/guestCount (`apps/api/src/booking/local-pms.provider.ts:416-433`). The inspected group catalog query checks active rate-plan currency and a selected room's type membership, not `room_types.max_occupancy` (`multi-room-booking.service.ts:335-360`). The inspected quote rules check property stay windows (`quote.service.ts:291-310`), and the group path does not check capacity again. Whether capacity is enforced outside these paths is **NEEDS VERIFICATION** before making a system-wide capacity claim.

**Recommended narrowed MBA-003 record:** keep HIGH for reproducible valid multi-adult quote rejection and quote/persist occupancy divergence. Say “may store differently if SQL succeeds” and “no group capacity check in inspected path”; do not claim a completed database insert or confirmed Clock over-occupancy. Add order API tests for one-adult quote plus changed `guestCount`, multi-adult and children quotes, and persisted child occupancy. Decide whether the order API should accept adults/children and how child ages are represented before implementing a provider-specific contract.

## MBA-004: distinct group payment and provider paths

**VERIFIED FINDING (source/control flow; HIGH, split by consequence):** The group path validates the signed quote, nightly-rate presence, catalog, and local availability, and holds all requested rooms before INSERT. `lockInventory` orders physical-room and pooled type locks; `reserveAll` throws `MultiRoomAvailabilityError` on either failed reservation, which `create` catches after the transaction, returning `AVAILABILITY_FAILED` (`apps/api/src/booking/multi-room-booking.service.ts:81-125,228-234,280-346`). The existing database-backed, provider-stubbed group test checks that a failed second pooled unit leaves zero booked units and zero bookings (`apps/api/test/multi-room-booking.e2e.spec.ts:257-318`). This is counterevidence to any claim that local group reservation is non-atomic. The test was inspected, not rerun.

The group path does **not** call `LocalPmsProvider.validateRoomSelection` or `prePaymentClockAvailabilityFailure`. Its `validCatalog` only confirms rate plan/type and optional selected room membership (`multi-room-booking.service.ts:335-360`); it neither reads `booking_mode` nor runs MIXED same-price auto-assignment. Therefore a specific `roomId` can take the physical-room reservation branch even for `ROOM_TYPE_ONLY`, and an omitted `roomId` can take the pooled branch for `INDIVIDUAL_ROOM_ONLY`, subject to local availability. In MIXED, an omitted `roomId` also remains pooled rather than receiving single-booking's same-price physical-room assignment (`apps/api/src/booking/local-pms.provider.ts:1525-1547,1562-1575`). The single-booking online path calls Clock final availability just before checkout and throws to roll back on a failed check (`local-pms.provider.ts:165-195,524-555,634-637`). No equivalent call appears between group reservation and checkout (`multi-room-booking.service.ts:189-207`). A valid earlier Clock quote and local hold are counterevidence to “no availability check at all,” but do not establish final Clock availability. Actual sold-out payment or Clock rejection is **NEEDS VERIFICATION**; this is a missing guard, not an observed provider outcome.

For nonzero totals the group `paymentMethod` checks the property toggle and requested method (`multi-room-booking.service.ts:362-399`), then selects a provider and creates the checkout **after** holds and inserts (`:189-207`). A connected credential is checked inside the real Stripe/PokPay providers (`apps/api/src/payments/stripe-payment.provider.ts:38-50,215-222`; `apps/api/src/payments/pokpay-payment.provider.ts:54-60,151-162`). Thus “gateway readiness is never enforced” would be wrong; it is enforced late, and a provider `ok: false` leaves the group in the failed-Result transaction path. The registry itself only selects a provider (`apps/api/src/payments/payment-provider-registry.ts:14-17`). No gateway readiness or Clock final-availability guarantee was established by the quoted price.

The zero-total group selects `FREE`, inserts children directly as `CONFIRMED`, and bypasses all later branches (`multi-room-booking.service.ts:127-133,161-223,362-369`). There is no `isClockConnected` or `attachRealReservation` call for `FREE`, so a Clock-connected free group is locally confirmed without this path creating Clock reservations. Nonzero `PAY_AT_HOTEL` attaches each child when Clock-connected, retaining a failed child's unknown-result state while attempting siblings; the local-only branch confirms children (`:161-187`). Paid Stripe/PokPay children attach only after verified payment via `LocalPmsProvider.continueMultiRoomOrderAfterPayment` (`apps/api/src/booking/local-pms.provider.ts:870-930`). The existing unit-003 counterexample and group e2e test show a forced second-child Clock failure preserving the anchor charge, first confirmed child, second `PMS_UNKNOWN_RESULT`, and manual review (`docs/audit/investigations/MBA-AUDIT-003.md:13`; `apps/api/test/multi-room-booking.e2e.spec.ts:613-658`). That is counterevidence to a blanket group rollback or blanket “group never attaches Clock” claim. The e2e Clock service is stubbed (`multi-room-booking.e2e.spec.ts:117-164`), so it does not prove real Clock behavior. The free-Clock path lacks a dedicated behavioral test in the inspected set.

**VERIFIED FINDING (source/transaction semantics; HIGH):** When the provider is absent or `createCheckoutSession` resolves `ok: false`, the group returns an error `Result` from its `execute` callback **after** `reserveAll` and child INSERT (`multi-room-booking.service.ts:122-159,193-207`). `withIdempotency` stores that error with status `FAILED` and returns normally (`:427-472`). `TenantDatabaseService.withTenantTransaction` directly returns Prisma's interactive transaction callback (`apps/api/src/tenancy/tenant-database.service.ts:19-43`); the order controller only passes the result through `noConflict` (`booking.controller.ts:100-115`). There is no group wrapper converting this failed checkout `Result` into an exception. The local writes therefore commit on this source path if the transaction itself completes. In contrast, a thrown provider error, SQL error, timeout, or `MultiRoomAvailabilityError` escapes and rolls the transaction back. Single-booking explicitly throws `CheckoutSessionCreationError` for a false checkout result and catches it outside the transaction (`local-pms.provider.ts:548-555,634-637`). This is a control-flow/Prisma semantics conclusion, not a real PostgreSQL reproduction of the failed-checkout branch.

On a committed failed-Result branch, the caller receives an error without child IDs/order reference while the newly inserted children remain `PAYMENT_PENDING`; the same idempotency key replays the stored error (`multi-room-booking.service.ts:127-159,199-207,444-471`). Call these holds **not returned to that caller**, rather than categorically inaccessible: staff or a separately known booking ID may still reach a booking. The normal expiry worker polls `PAYMENT_PENDING` candidates after 30 minutes, 100 per sweep, and calls group-aware `expirePaymentPending` (`apps/api/src/payments/payment-expiry.service.ts:11-14,63-85`; `local-pms.provider.ts:933-976`). For pooled children that function decrements `booked_units` before `EXPIRED` (`:955-965`). Physical rooms have no booked-unit counter to decrement; their occupancy is derived from overlapping bookings in active statuses, and `EXPIRED` is absent from that predicate (`apps/api/src/tenancy/availability.service.ts:457-465,605-641`). Thus the holds are **not necessarily permanent** if the sweep runs and succeeds. The failed idempotency result persists independently; no retry that resumes checkout was found in this inspected path. Sweep execution and actual release under a failed checkout remain **NEEDS VERIFICATION**.

**Recommended narrowed MBA-004 record:** retain HIGH, but separate (1) FREE Clock omission, (2) group mode/assignment and final Clock availability divergence, and (3) committed pending children plus failed operation on a returned checkout error. Replace “inaccessible pending holds” with “child IDs absent from the failed response; time-bound pending holds require expiry or staff recovery.” Replace “gateway readiness absent” with “credential readiness checked only after local hold/INSERT, and its returned failure currently commits them.” Test FREE on Clock-connected property, both invalid property-mode selections and MIXED assignment, final Clock no-availability before group checkout, provider false Result versus thrown error, idempotent replay, and pooled versus physical expiry. Use a database-backed test with provider/Clock stubs for transaction effects; reserve live-provider claims for separately authorized validation.
