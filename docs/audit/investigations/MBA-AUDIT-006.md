## Disposition proposed to Astra

**VERIFIED FINDING (source/control flow; HIGH):** An otherwise permitted `LocalPmsProvider.cancelBooking` of a pooled booking in `PMS_CREATION_PENDING` or `PMS_UNKNOWN_RESULT` can write `CANCELLED` without decrementing the previously reserved `inventory_units.booked_units`. Both single and group cancellation use the same incomplete release predicate. The resulting counter overstates sold stock for the affected nights until an independent correction; the inspected normal cancellation, expiry, and read-only Clock consistency paths do not repair it. A committed database outcome was not reproduced in this unit. “Permanently” is too absolute because a future manual repair/migration could reconcile the counter.

The broad MBA-005 wording needs narrowing. `PMS_REJECTED` is allowed by the state graph but is not produced by the normal `LocalPmsProvider` Clock attachment path, which uses `PMS_UNKNOWN_RESULT` on POST failure. The separate `ClockBookingService.createBooking` can produce `PMS_REJECTED`, but that path does not reserve pooled units. `MANUAL_REVIEW` is likewise an allowed state, while the inspected failure path records a `ManualReviewItem` and generally leaves booking status at `PMS_UNKNOWN_RESULT` or `PMS_CREATION_PENDING`; no normal writer of booking status `MANUAL_REVIEW` was found in the scoped search. For these two states, a leaked counter is conditional on a row already owning a pooled hold. Neither status alone proves ownership.

## Ownership and release map

| State or path | Pooled counter ownership in inspected flow | Cancellation / expiry effect |
| --- | --- | --- |
| `DRAFT`, `QUOTED`, `INVENTORY_REVALIDATING`, `AVAILABILITY_FAILED` | No successfully reserved unit yet in single creation | Graph may allow cancellation for the first three, but there is no counter to release (`local-pms.provider.ts:489-521`; `booking-state-machine.ts:6-18`). |
| `PAYMENT_PENDING` | Single reservation has succeeded; group `reserveAll` precedes child INSERT (`local-pms.provider.ts:489-541`; `multi-room-booking.service.ts:122-159,294-333`) | Single/group cancellation decrements. Payment expiry also decrements before `EXPIRED` (`local-pms.provider.ts:933-985,1082-1094,1290-1302`). |
| `PAYMENT_NOT_REQUIRED` | Single reservation has succeeded; transition to `PMS_CREATION_PENDING` follows inside the same creation transaction (`local-pms.provider.ts:574-586`) | State graph allows cancellation, but cancellation predicate omits it. No ordinary committed pause in this state was established. |
| `PMS_CREATION_PENDING` | Hold persists from the earlier reservation, unless the transaction that reserved it rolled back. Group pay-at-hotel children are inserted directly in this state (`multi-room-booking.service.ts:127-159`). | Cancellation graph allows it; neither single nor group predicate decrements (`booking-state-machine.ts:30-37`; `local-pms.provider.ts:1082-1095,1290-1306`). |
| `PMS_UNKNOWN_RESULT` | Hold persists if entered from a committed held booking; Clock attachment POST failure transitions here without release (`clock-booking.service.ts:619-652`). | Cancellation graph allows it; release predicates omit it (`booking-state-machine.ts:48-53`). |
| `PMS_REJECTED`, `MANUAL_REVIEW` | Potentially held after a state transition from a held PMS state, but ownership is not established merely by these labels. Normal local attachment does not set either booking status (`clock-booking.service.ts:453-465,625-677`). | Graph allows cancellation and release predicates omit both (`booking-state-machine.ts:54-55`). Conditional risk, not a proved ordinary local creation route. |
| `PMS_CONFIRMATION_PENDING`, `CONFIRMED` | Hold persists for pooled bookings. | Both cancellation paths decrement before `CANCELLED` (`local-pms.provider.ts:1082-1108,1290-1314`). |
| `CANCELLED`, `EXPIRED` | Should no longer own the pooled hold. | Terminal in the graph. Expiry only accepts `PAYMENT_PENDING`, so it cannot later clean up a cancelled recovery-state booking (`booking-state-machine.ts:56-57`; `local-pms.provider.ts:939-965`). |

`AvailabilityService.reserveBookedUnits` and `releaseBookedUnits` change the per-night counter under a room-type advisory lock and row locks; release throws if subtraction would go below zero (`availability.service.ts:436-455,480-487,543-590`). Sellable pooled stock subtracts `booked_units` from configured `available_units` (`availability.service.ts:101`). There is no booking-level hold claim or per-booking release flag in this method: the caller's status/`roomId` predicate decides whether to call it.

Physical-room bookings follow a different model. `reserveRoom` locks the room and checks overlapping bookings; it does not increment `booked_units` (`availability.service.ts:457-465,605-641`). `CANCELLED` and `EXPIRED` are absent from that overlap predicate, so their transition removes local physical occupancy without a decrement. This note does not call that a pooled-counter leak. The same distinction is reflected in MBA-AUDIT-005's `PAYMENT_PENDING` expiry counterevidence.

## Reachability, guards, and counterevidence

Both public guest and staff DELETE handlers call `LocalPmsProvider` directly, including Clock-connected properties (`booking.controller.ts:144-171`; `staff-booking.controller.ts:30-49`). `PmsProviderRegistry` could route to Clock for other operations, but it is not the cancellation wrapper here (`pms-provider-registry.ts:24-40`). Single cancellation first checks identity, expected version, state transition, and for guests the self-service window. If Clock is connected and the row has `externalBookingId`, it requires a successful `cancelRealReservation` before refund/release/status effects (`local-pms.provider.ts:1015-1067`). Clock cancellation itself performs GET then PUT and returns failure on either failed call (`clock-booking.service.ts:1375-1393`). Such a rejected request does **not** demonstrate the leak; a staff cancellation of a recovery-state booking with no external ID can pass this Clock sub-step, subject to its other gates.

One concrete source route to a committed held recovery state is pay-at-hotel single creation: reserve first, enter `PMS_CREATION_PENDING`, call Clock attachment, and return its failed `Result` inside the idempotency/tenant transaction (`local-pms.provider.ts:489-507,574-604,622-633`). `attachRealReservation` transitions failed POST/rate paths to `PMS_UNKNOWN_RESULT` without release (`clock-booking.service.ts:541-565,619-677`). Earlier credential, missing-guest, or missing-mapping failures record review but do not transition, so a returned failure can leave `PMS_CREATION_PENDING` (`clock-booking.service.ts:472-536`). `withIdempotency` persists the returned result rather than throwing (`local-pms.provider.ts:1435-1448`). A thrown exception or transaction failure would roll back the hold and is not this case. The separate paid Stripe continuation rollback issue in MBA-AUDIT-003 means its failure branch must not be treated as proof of a committed recovery state.

Group creation reserves pooled units before child INSERT, then writes pay-at-hotel children as `PMS_CREATION_PENDING` and continues attachment independently (`multi-room-booking.service.ts:122-175,294-333`). A failed child can therefore retain a held recovery state while siblings confirm. Group cancellation validates all children before provider calls. On a failed Clock cancellation for a child with an external ID it records manual review, skips local cancellation for that child, continues siblings, and returns `ORDER_CANCELLATION_PARTIAL_FAILURE`; successful children pass through `applyMultiRoomCancellation` and the same narrow release predicate (`local-pms.provider.ts:1157-1245,1282-1314`). Existing database-backed group tests with a stubbed Clock cancellation show `CANCELLED`/`CONFIRMED` partial outcome, not a recovery-state counter test (`apps/api/test/multi-room-booking.e2e.spec.ts:467-500`). A group response error can therefore coexist with already cancelled siblings; it is not evidence that every child's hold leaked or that all effects rolled back.

For a pooled recovery-state child without an external ID, or after successful Clock cancellation, the path reaches `applyMultiRoomCancellation`, omits the decrement, and writes `CANCELLED`, provided the transaction completes. Single cancellation has the equivalent omission (`local-pms.provider.ts:1059-1108`). An automatic refund failure records review but does not by itself stop the single cancellation (`local-pms.provider.ts:1069-1080,1362-1385`). Replaying the same cancellation idempotency key returns the stored result without rerunning release; a new cancellation request sees terminal `CANCELLED` and fails the transition check (`local-pms.provider.ts:1033-1037,1411-1448`; `booking-state-machine.ts:56-57`). The inspected counter writes in API source are the reservation/release calls and `AvailabilityService.adjustBookedUnits`; Clock consistency is explicitly read-only (`clock-booking-consistency.service.ts:80`). No automatic post-cancellation counter repair was found in this bounded search.

## Recommendation and verification limit

Keep MBA-005 at **HIGH / NOW** for the `PMS_CREATION_PENDING` and `PMS_UNKNOWN_RESULT` pooled-booking paths. Describe `PMS_REJECTED` and booking-status `MANUAL_REVIEW` as conditional on proven prior hold ownership, and replace “permanently suppress” with “continues suppressing sellable stock until separately reconciled.” Model the hold and release exactly once independent of ambiguous PMS status, with transactional state/counter tests for single and group, external-ID/no-external-ID, provider success/failure, idempotent replay, and pooled versus physical rooms. A database-backed provider-stub test is needed to verify committed counters and transaction behavior; any real Clock or deployed impact remains **NEEDS VERIFICATION**. Existing tests were inspected, not rerun; no isolated probe was necessary to resolve the source branch.
