# ADR-0020: Single login, role-routed to a Platform Admin dashboard or the Tenant dashboard

Status: Accepted — point 5 (dashboard sequencing/bundling) superseded by [ADR-0023](ADR-0023-platform-admin-dashboard-resequencing.md); points 1-4 (routing mechanism) unaffected
Date: 2026-07-31

## Context

`apps/web` today serves exactly one dashboard experience: the tenant-facing one. ADR-0010 fixed how that works — a single login/session (Milestone 1's `must_session` cookie), `/dashboard` as a tenant picker for users with multiple memberships, and `/dashboard/:tenantId/...` as the tenant-scoped dashboard itself, gated by Milestone 1's role (Tenant Owner/Admin) and capability (Property Staff template + overrides) model. Milestone 8 (not yet kicked off) is scoped to build exactly this: "reservations, payments, guests, staff, settings" for a hotel's own staff.

Separately, the guest-facing side (ADR-0016) is not part of this at all — the WordPress plugin retrofit has no login, no session, no dashboard.

What has never had a home is **MUST's own internal team** operating the platform itself — across tenants, not inside one. The RBAC scaffolding already has a `Role.PlatformAdmin` enum value (`apps/api/src/tenancy/roles.decorator.ts`) from Milestone 1, but nothing consumes it: no route, no dashboard, no platform-scoped capability model, and no design work. The Figma admin-dashboard page built so far (`01 — Admin Dashboard`, 22 sections: Auth, Dashboard, Reservations, Calendar, Accommodations, Rates & Pricing, Availability, Payments, Guests, Emails, Coupons, Reports, Provider & Integrations, Settings, WordPress Plugin config, Staff/Roles/Audit, Notifications, plus responsive/accessibility/QA references) was checked node-by-node: it is entirely single-tenant scoped — no multi-tenant switcher, no MUST-internal screens — i.e. it is the Milestone 8 tenant dashboard, not a platform-admin surface.

The owner wants one login window that, based on the authenticated user's role/membership, sends them to one of two different dashboard experiences: a platform-operations dashboard for MUST's own admin and supporting staff, versus the existing tenant dashboard for a hotel's Owner/Admin/Property Staff. This ADR fixes that shape before Milestone 8 (which builds the tenant half) or any future platform-dashboard milestone starts, so neither is built assuming it's the only dashboard.

Four sub-questions were resolved with the owner via explicit options/trade-offs before finalizing this ADR: role precedence when an account could plausibly reach both dashboards, whether the platform dashboard is a separate deployed app, how much role granularity MUST's internal team needs on day one, and when the platform dashboard actually gets built relative to the roadmap. All four are decided below.

## Decision

1. **One login, one session mechanism.** Platform users authenticate through the exact same login page and `must_session` cookie as tenant users. No separate auth flow, no separate credential store.
2. **Redirect target is derived from role, evaluated at post-login routing time:**
   - A user holding the platform role (`PLATFORM_ADMIN`) is routed to a new top-level route tree, `/platform/...`, distinct from `/dashboard/...`.
   - Every other user follows ADR-0010's existing tenant routing unchanged: `/dashboard` (picker) → `/dashboard/:tenantId/...`.
   - **Dual roles are forbidden by policy, not resolved by routing precedence.** A user account is never simultaneously a platform-role holder and a tenant member. Account provisioning (Milestone 1's invite flow, and whatever provisions `PLATFORM_ADMIN` accounts) must enforce this — a platform-role account cannot accept a tenant staff invite, and a tenant-membership account cannot be granted `PLATFORM_ADMIN`. This removes the ambiguity at the source instead of needing a precedence rule or a "choose dashboard" step at login. If a MUST staff member genuinely needs to inspect a specific tenant's dashboard (support/debugging), that is a separate, not-yet-designed capability (e.g. future impersonation) and is explicitly out of scope here — it is not solved by giving their platform account a tenant membership.
3. **Both dashboards stay in one Next.js app (`apps/web`), one codebase, one deploy — not two separate applications.** They are two top-level route trees sharing the same session/auth code, layout primitives, and design-system components/tokens (the Figma foundations page already covers this). Physical separation (a second deployed app, a distinct subdomain build) is not done preemptively; it's deferred until there's a concrete driver (see Consequences).
4. **Platform-side access is a single role for now — `PLATFORM_ADMIN`, already scaffolded — not a capability-template system.** Unlike Property Staff (Milestone 1's template + override model), the platform dashboard does not get its own capability/template system in this ADR. MUST's internal team is small enough today that one role is sufficient. A template/capability system analogous to Property Staff's is only built once there are actually distinct platform roles to separate (e.g. support vs. billing ops) — not speculatively now.
5. **The platform dashboard is folded into Milestone 9 (Platform Billing), not left as an unscheduled backlog item or split into its own new milestone.** Milestone 9 already builds subscription/plan-state backend across tenants — the core of what a platform admin needs to see — so building the platform dashboard's UI alongside it avoids standing up the same cross-tenant backend surface twice. Milestone 8 proceeds as-is, building only the tenant dashboard (the Figma design already matches it); Milestone 9's task table, written at its own kickoff, is expected to include the `/platform` dashboard shell and views alongside its billing-backend tasks.

## Consequences

- `apps/web` gains a second top-level route namespace (`/platform`) alongside `/dashboard`; both read the same session but render different navigation shells and are gated by different role checks.
- `Role.PlatformAdmin` gets a real consumer for the first time; a `@Roles(Role.PlatformAdmin)` guard on platform-only API routes is now meaningful once those routes exist (Milestone 1's guard mechanism already supports this — no new backend primitive needed for the role check itself).
- Account provisioning gets a new invariant to enforce: a `PLATFORM_ADMIN` account must never also hold a `tenant_membership` row, and vice versa. Milestone 1's staff-invite flow (`acceptExisting`) and whatever process provisions platform accounts both need a check for this — a cross-tenant/cross-role isolation test similar in spirit to Milestone 1's Task 8 (cross-tenant test suite) should cover it once `/platform` exists.
- No capability/template system is built for platform staff by this ADR — `PLATFORM_ADMIN` is the only platform role. If/when a second platform role is needed, that's new schema/guard work at that time, not something this ADR pre-builds.
- The existing Figma "01 — Admin Dashboard" page is confirmed as the Milestone 8 tenant-dashboard design, not the platform dashboard. A separate Figma page/section is needed later for the platform-admin surface; no rework of the existing design is implied by this ADR.
- No change to ADR-0010 (tenant-URL routing) or ADR-0016/ADR-0017 (guest-facing, login-free model) — this ADR is additive to the former and unrelated to the latter.
- Because both dashboards ship from one app/build, a dependency issue or outage affecting one route tree can in principle affect the other. Accepted for now given team size and the absence of any concrete isolation requirement; revisit if the platform dashboard later needs a different deploy cadence, network/security boundary, or on-call ownership than the tenant dashboard.
- Milestone 8's kickoff should note that Milestone 9's eventual task table will include the `/platform` dashboard, so Milestone 8's own tasks don't need to (and shouldn't) accidentally grow to cover it.

## Alternatives considered

- **Separate deployed application for the platform dashboard** (e.g. `apps/platform-admin`): rejected for now — no concrete requirement for stronger isolation exists yet, and this repo's established pattern (ADR-0016 declining to build a green-field guest widget preemptively; the backlog's "only if an actual tenant needs it" items) is to not build infrastructure ahead of an actual need. Revisit once/if a real isolation driver shows up.
- **Session-based "current dashboard mode"** instead of separate route trees: rejected for the same reason ADR-0010 rejected session-based selected-tenant state — it reintroduces cross-tab/cross-context desync risk. URL-based separation (`/platform` vs `/dashboard`) keeps routing explicit and stateless.
- **Modeling platform capabilities as a pseudo-tenant** inside the existing tenant-scoped capability tables: rejected — platform capabilities apply across all tenants and to platform-owned data (billing oversight, cross-tenant support tooling) that doesn't fit the `tenant_id`/`property_id`-scoped RLS model. A parallel, explicitly non-tenant-scoped capability system is more honest to what it actually governs, if/when it's built.
- **Platform role takes precedence when an account holds both roles** (rather than forbidding the combination): rejected — it solves the routing ambiguity but leaves the underlying account-modeling ambiguity (does this user's access include tenant data or not?) unresolved, and quietly invites scope creep toward using it as an ad-hoc impersonation mechanism. Forbidding the combination is a cleaner invariant; real support/impersonation access is deferred as its own explicit future capability instead.
- **Full capability-template system for platform staff now**, mirroring Property Staff: rejected as premature — MUST's internal team is small enough today that one role covers it; building the template/override machinery ahead of having a second role to justify it is exactly the kind of speculative abstraction this codebase avoids elsewhere.
- **Platform dashboard as its own new milestone, or left as an unscheduled backlog item**: rejected in favor of folding it into Milestone 9 — it would mean either inserting a milestone the roadmap didn't plan for, or building Milestone 9's cross-tenant billing backend with no UI consumer until some later, undefined point.
