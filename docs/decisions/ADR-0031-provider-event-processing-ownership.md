# ADR-0031: Provider-event processing ownership (fencing token) and completed-but-unreconciled parking state

Status: Accepted (amended five times — four same-day (2026-09-19), one on 2026-09-23 — see the "Corrective update" sections below; the most recent amendment describes the actual, currently-implemented guarantee)
Date: 2026-09-19

## Context

Milestone 21 Task 22 (durable Clock webhook processing) first added `provider_events.status`/`.attempts` lifecycle tracking and a scheduled recovery sweep. A same-day corrective review found the design still had two real gaps:

1. **No exclusive processing ownership.** The guarded status transitions (`UPDATE ... WHERE status <> ALL(forbidden)`) stopped a *finished* attempt's status from being overwritten, but `QUEUED -> QUEUED` was never forbidden — so two overlapping executions of the same logical event (BullMQ's own documented stalled-job caveat: a job whose lock isn't renewed in time can be reassigned to a second worker while the first is still actually running) could both pass the claim guard and both call the real hydration effect (a live Clock API call plus a local DB upsert) concurrently. Relying on the hydration upsert's own idempotency was explicitly rejected as sufficient proof by the reviewer — ownership needs to gate *application of the effect*, not just the final status write.
2. **A single default forbidden-status list was too permissive for every caller.** Ingestion's post-enqueue `QUEUED` write, the sweep's `QUEUED`/`FAILED` writes, and the worker's own claim all shared one default (`forbiddenFrom = ['HYDRATED', 'IGNORED']`), which never excluded `FAILED`. A stale ingestion operation or sweep snapshot that read a row before it was marked `FAILED` could resurrect it back to `QUEUED` after the fact, silently overriding BullMQ's own deliberate "exhausted attempts, stop" policy with a side channel.

## Decision

**Fencing token, reusing BullMQ's own per-attempt token.** `provider_events` gains a `processing_token` column. Every processing attempt claims ownership by writing BullMQ's own `job.token` (the same value BullMQ already uses internally for lock renewal and is guaranteed fresh per attempt, including on stalled-job reassignment — no new identity is invented). Every subsequent write for that attempt — the pre-effect ownership re-check, and the terminal `HYDRATED`/`IGNORED`/`FAILED` write — is guarded by `processing_token = $myToken`, on top of the existing status guard. A stale attempt that finishes after a replacement has taken over always loses this comparison (0 rows affected) and cannot finalize over the newer attempt's outcome. The pre-effect check means a stale attempt that hasn't yet called the hydration service when it loses ownership skips the call entirely, rather than only discovering the loss at the final write.

**Explicit allowed-from list per caller, no shared default.** `guardedTransitionSql` now requires an explicit `allowedFrom` array on every call — there is no default. Every caller states exactly which prior states it may transition out of:

| Caller | Transition | Allowed from |
| --- | --- | --- |
| Worker claim | → `QUEUED` (+token, +attempts) | `RECEIVED`, `QUEUED` |
| Worker finalize | → `HYDRATED` / `IGNORED` / `FAILED` | `QUEUED` (+ token match) |
| Worker `'failed'` listener | → `FAILED` | `RECEIVED`, `QUEUED` (+ token match against the failed attempt's own `job.token`) |
| Ingestion / sweep, job missing | → `QUEUED` | `RECEIVED`, `QUEUED` |
| Ingestion / sweep, job failed | → `FAILED` | `RECEIVED`, `QUEUED` |
| Ingestion / sweep, job completed but row non-terminal | → `NEEDS_RECONCILIATION` | `RECEIVED`, `QUEUED` |

`FAILED` never appears in an `allowedFrom` list — nothing automatic (ingestion, sweep, or the worker's own claim) can ever move a `FAILED` row back toward processing. This is deliberate: `FAILED` means BullMQ already exhausted its configured attempts, a policy decision that must not be silently bypassed by a flood of duplicate SNS redeliveries or a sweep tick that happens to run before the async `'failed'` listener does. Retrying a `FAILED` event is an explicit, documented operator action (see the runbook procedure in `docs/integrations/clock/webhooks-and-reconciliation.md`), not an automatic one.

**`NEEDS_RECONCILIATION`: a durable parking state, not a new automatic pathway.** Under the fencing-token design, a genuinely committed terminal write is required for BullMQ to observe the processor function returning successfully — if the write fails to commit, the exception propagates and BullMQ sees a failed attempt, not a silent success. The "completed job, non-terminal row" gap this state exists for is therefore now confined to: (a) legacy rows created before this design existed, whose BullMQ job (if not already aged out of Redis retention) is discovered `completed` by the sweep/ingestion's `reconcileJob` check; and (b) any residual race this analysis has not fully ruled out. Rather than guess at HYDRATED vs IGNORED or leave the row rotating through warning logs forever, the row is moved to `NEEDS_RECONCILIATION` (excluded from the sweep's `RECEIVED`/`QUEUED` candidate set — so the underlying BullMQ job later aging out of retention can never silently flip this back into automatic reprocessing) and a `ManualReviewItem` (category `UNKNOWN_RESULT`) is recorded pointing an operator at the exact row and the real Clock resource to check directly.

## Consequences

- One additive migration: `provider_events.processing_token` (nullable text) and a new `ProviderEventStatus` enum value, `NEEDS_RECONCILIATION`. No data migration; existing rows are unaffected (`processing_token` is `NULL` until first claimed under the new code).
- `ClockWorkerService` gains a dependency on `ManualReviewService` (already used elsewhere in the Clock integration for the same "something needs a human to look" purpose).
- Rollback of the companion RLS-policy migration (`20260919120000_provider_events_recovery_sweep`, `provider_events_platform_admin_read`) removes the sweep's ability to read across tenants at all — its query returns zero rows for every tenant, not just other tenants' — degrading recovery back to redelivery-dependent only. Per-tenant webhook ingestion and processing are unaffected, since they never rely on that policy.
- A `NEEDS_RECONCILIATION` row requires a human to resolve (documented runbook procedure); this task does not add a UI or admin API for it, matching the existing constraint against adding a general replay/admin surface without a separate authorization/audit review.

## Alternatives considered

- **A separately generated UUID token per attempt**, rather than reusing `job.token`. Rejected: BullMQ's own per-attempt token already has exactly the freshness/invalidation semantics needed (a new one on stalled-job reassignment); inventing a parallel identity would only add a second concept to keep in sync with the first without adding any real protection.
- **Holding a Postgres lock for the entire hydration call, including the outbound HTTP request to Clock.** Rejected, and still rejected after the correction below: tying up a database connection/lock for the duration of an external API round-trip is a materially worse operational cost than a short, HTTP-free locked transaction. This does **not** rule out a short transaction opened only *after* the HTTP fetch returns — see the correction below, which does exactly that.
- **Treating the "completed but unreconciled" gap as fully closed and doing nothing further.** Rejected by the reviewer: even a narrowed, legacy-only gap needs a durable, actionable resolution rather than being left as an indefinite warning-log loop.

## Corrective update, 2026-09-19 (third review, same day)

The first version of this ADR described the ownership check as a plain read (`ownsEvent()`) performed once, immediately before calling the hydration service — a check-then-act race, not a fence: nothing stopped a replacement attempt from claiming and finishing between that check and the effect actually being applied. The decision below corrects the actual mechanism; the "Decision" section above is superseded by this one where they conflict, but is kept for history per the documentation-maintenance rule against rewriting ADR bodies to look compliant after the fact.

**Real fencing at the business-write boundary, not a preceding check.** `ClockBookingHydrationService.hydrateBooking()` and `ClockFolioHydrationService.hydrateFolio()` now accept an optional `EventOwnership` (`{ eventRowId, token }`). The outbound Clock HTTP call still happens first, entirely outside any transaction (per the original decision's own reasoning — never hold a lock across a network round-trip). Only *after* that fetch returns does a transaction open, and the **first statement inside it** is `SELECT status, processing_token FROM provider_events WHERE id = $1 FOR UPDATE` — a real Postgres row lock held for the rest of that transaction. If the row isn't `QUEUED` with this attempt's token, the transaction does nothing further and returns `{ outcome: 'ownership_lost' }`; no local effect is applied. If ownership holds, the row lock is held through the entire local effect (the booking/folio upsert, guest/catalog-mapping reads and writes, a `missing_room_type_mapping` ManualReviewItem where applicable) **and** the event's terminal status write (`HYDRATED`/`IGNORED`/`FAILED`, token cleared) — they commit together in one transaction, or a failure at any point rolls back all of it together. No other attempt's claim or finalize can interleave between the lock being acquired and the transaction committing, because Postgres's row lock genuinely blocks a concurrent writer until this transaction ends. `ClockWorkerService` no longer performs its own pre-effect check or its own success/failure status write for these two event families — that responsibility now lives inside the transaction that actually applies the effect, where it can be atomic with it. The worker still owns claiming (see below) and the two paths that never call a hydration service at all (no object id; an unsupported event type), which still finalize through the worker's own token-guarded write.

**Claim ordering: a second fencing dimension, not just token identity.** (Superseded by the fourth corrective update below — this paragraph used `job.attemptsMade` as the ordering signal, which turned out to be the wrong field; kept for history.) The token alone answers "is this the current owner," but not "is this claim actually newer." A claim UPDATE is a normal, unlocked write — if a stalled attempt A's claim reaches Postgres *after* a fresher replacement attempt B's claim (a real possibility: A could be delayed by GC pause, network jitter, or simply because BullMQ decided it was stalled while A's own claim call was still in flight), A's claim would silently steal ownership back from B purely because of arrival order, even though B is the legitimately current attempt. `provider_events` gains `processing_attempt`, recording the claimant's BullMQ `job.attemptsMade` — the only reliable signal that distinguishes "obsolete" from "fresh" once two attempts share the same job id, since BullMQ increments it on every real dispatch including a stalled-job reassignment. A claim only succeeds if no attempt has claimed yet or the row's recorded `processing_attempt` is `<=` the claiming attempt's own; a lower-numbered claim arriving late is rejected (0 rows affected), leaving the higher-numbered attempt's ownership intact.

**Atomic parking.** The original "park as `NEEDS_RECONCILIATION`" implementation wrote the guarded status UPDATE and the `ManualReviewItem` in two separate transactions — a failure recording the item (or a crash between the two) could leave a row silently parked with no actionable trail, exactly the failure mode this state exists to prevent. Both `ClockWebhookService` and `ClockWorkerService` now perform the guarded UPDATE and `ManualReviewService.recordInTransaction()` inside the **same** tenant-scoped transaction: the UPDATE runs first, and the item is only inserted if it actually affected the row (so a losing concurrent parking attempt creates no item), and any failure inserting the item rolls the status write back too, leaving the row exactly as it was for a later attempt to retry cleanly.

**Migration idempotency.** `20260919130000_provider_events_ownership_and_reconciliation` was rewritten to use `ADD COLUMN IF NOT EXISTS` (both `processing_token` and the new `processing_attempt`) and `ADD VALUE IF NOT EXISTS` for the enum — verified by applying it fresh against a disposable Postgres from an empty database (all 89 migrations, clean) and then re-executing its exact SQL a second time directly against the same database with no error and no duplicated enum value. (Rollback guidance below is superseded by the fourth corrective update.)

## Corrective update, 2026-09-19 (fourth review, same day)

**`job.attemptsMade` was the wrong claim-ordering signal — replaced with `job.attemptsStarted`.** The third correction's `processing_attempt <= claiming attempt's own` guard used BullMQ's `job.attemptsMade`, assuming it increments on every dispatch. Verified against the installed `bullmq@6.0.0` source, that assumption was wrong: `attemptsMade` only increments when an attempt genuinely *fails* (see `Worker`'s failure-handling path); a job reassigned after stalling — the exact scenario this guard exists for — has **not** failed, so two overlapping activations of the same job (the original attempt, still actually running, and its stalled-reassignment replacement) can share the same `attemptsMade` value. Under the old `<=` guard, that tie let the obsolete attempt's late-arriving claim silently reclaim ownership from the legitimate newer attempt — the exact bug this mechanism was built to prevent, reintroduced through the wrong field.

The correct signal is `job.attemptsStarted`, confirmed directly in the installed package's compiled Lua (`prepareJobForProcessing.lua`): every real activation — including a stalled job's genuine reassignment — issues an unconditional `HINCRBY jobKey "ats" 1` against the Redis field backing `attemptsStarted`, before the job handler ever runs. It increases monotonically on dispatch, not on failure, which is exactly "is this claim newer" rather than "has this claimant failed yet."

**The guard is now a combined token+generation comparison, not a bare `<=`.** `claimEventSql` (`clock-provider-event-status.ts`) replaces the old `setToken`/`claimAttempt` options on `guardedTransitionSql` with a dedicated claim function:

- no current claimant (`processing_attempt IS NULL`) → always allowed;
- a strictly newer generation → allowed, overwrites the claimant;
- the *same* generation and the *same* token → allowed as a no-op re-claim (the same attempt retrying its own claim write after a transient DB error must not be treated as a conflict with itself);
- the *same* generation with a *different* token → **rejected** (two distinct dispatches must never silently replace each other merely because they happen to share a generation number);
- a strictly older generation → rejected (the original obsolete/late-claim case).

This satisfies the reviewer's explicit requirement that an equal generation permit only an idempotent same-token claim, never a cross-attempt replacement.

**Job recreation must reset the generation counter, or a fresh job can be permanently locked out.** (Superseded by the fifth corrective update below — the blind `clearToken: true` reset described here turned out to have its own race; kept for history.) `processing_attempt` is scoped to one BullMQ job's lineage; when ingestion or the sweep create a **new** job for a row whose old job disappeared (the `reconcileJob() === 'missing'` branch, both in `ClockWebhookService` and `ClockWorkerService`), the new job's own `attemptsStarted` restarts at 1 — but the row could still carry a much higher `processing_attempt` left over from the old, now-defunct job. Without a reset, the new job's first (low-generation) claim would be permanently rejected by the generation guard, forever, since nothing else ever raises the new job's generation past that stale high-water mark. Both re-enqueue paths now pass `clearToken: true` on that transition, which resets `processing_token`/`processing_attempt` to `NULL` alongside the status write — `claimEventSql`'s `NULL` case then unconditionally allows the new job's first claim. This is deliberately scoped to only the missing-job branch: it is the one place a genuinely new job lineage begins, so it can never be used by a stalled attempt to unlock its own reassignment.

**Proof through real BullMQ, not manually assigned attempt numbers.** The reviewer explicitly rejected manually setting different `attemptsMade`/`attemptsStarted` values as sufficient proof of the fencing behavior. `test/clock-webhook-recovery.e2e.spec.ts` now drives two real `Worker` instances against real Redis: attempt A's real Worker force-closes mid-job (stopping its lock-renewal timer, simulating a crashed process) with its Clock-fetch response gated so it stays paused; its lock is left to genuinely expire; a second real Worker's actual `moveStalledJobsToWait()` (BullMQ's own documented two-tick protocol) is driven twice to force a real stalled-job reassignment to attempt B, whose response is ungated and completes normally. Only after B has claimed and finished is A's gate released, and the test asserts A's resumed, now-stale claim cannot overwrite B's `processing_token`, cannot flip the row's terminal status, and never applies its own (stale) local effect — the booking row reflects only B's result. Distinct generation-ordering cases (strict ordering, same-generation/same-token, same-generation/different-token) are additionally proven deterministically at the SQL level (not practical to force reliably through real BullMQ timing for an exact tie), and dedicated tests cover the missing-job-recreation reset and the documented `FAILED -> RECEIVED` operator-retry path end to end.

**Corrected rollback guidance.** The `processing_token` / `processing_attempt` columns are **not** safe to drop "at any time" — every claim/fence/clear code path (`claimEventSql`, `guardedTransitionSql`, `ownershipLockSql`/`ownsRow`) reads and writes them as part of its normal control flow, not as an optional extra; dropping them while compatible code is still running turns every claim attempt into a hard SQL error, not a graceful NULL-tolerant no-op. The migration file's own header comment now documents the actual safe ordering: stop the worker/sweep (or deploy compatible code first) before dropping, let any in-flight attempt finish or genuinely stall out under the old code/columns, and note that a parked `NEEDS_RECONCILIATION` row's `processing_*` values are historical claim metadata, not required to resolve its `ManualReviewItem` — but are lost if the columns are dropped before anything of interest is exported. Preferred default: retain the additive columns during an application rollback (roll the application code back instead) rather than dropping them, which sidesteps this ordering entirely. PostgreSQL still has no supported way to drop a single enum value; `NEEDS_RECONCILIATION` remains permanently un-removable by a rollback migration, and the retirement story (stop writing it, resolve existing rows, leave the inert value in place) is unchanged.

## Corrective update, 2026-09-23 (fifth review)

**The fourth correction's job-recreation reset (`clearToken: true`) was itself an unguarded write with a real race.** Recreation is not one atomic step: ingestion/the sweep observe `reconcileJob() === 'missing'`, create a replacement BullMQ job, then reset `processing_token`/`processing_attempt` to `NULL` so the new job's low first generation isn't blocked by a stale high-water mark. The reset was a blind, unconditional write (`guardedTransitionSql` with `clearToken: true`, guarded only by `allowedFrom`) — but between "create the job" and "write the reset," the freshly created job's own worker can already have claimed the row for real (`claimEventSql`, setting a fresh non-null token and generation). A blind reset arriving after that claim would silently erase ownership a legitimate new attempt had already acquired, un-fencing an attempt that is still actively running. The same blind write also let two concurrent recreators (e.g. a duplicate SNS delivery reacting through ingestion, and a sweep tick, both genuinely observing the same row as `missing` at the same time) each stomp whatever the other had just written, with no coordination between them.

**Fix: the reset is now a real compare-and-swap against a snapshot, never a blind write.** `clock-provider-event-status.ts` gains `processingSnapshotSql` (a plain, unlocked read of a row's current `status`/`processing_token`/`processing_attempt` — deliberately not `FOR UPDATE`, for the same reason the outbound Clock fetch never runs inside a lock: a Redis round-trip must never hold a Postgres row lock open) and `resetForJobRecreationSql`, which only resets the row if `processing_token`/`processing_attempt` still hold *exactly* the values observed by that snapshot, taken immediately before the replacement job was created (`IS NOT DISTINCT FROM`, so an expected `NULL` is a valid, matchable value, not "skip this check"). If anything has claimed, finalized, or otherwise transitioned the row since that snapshot, the reset's `WHERE` clause fails to match and it affects 0 rows — the newer state is left untouched. This also correctly arbitrates concurrent recreators: when two callers snapshot the same pre-recreation values and both attempt the write, Postgres's row lock serializes them and only the first to commit succeeds; the second re-evaluates its `WHERE` clause against the row the first just changed and safely no-ops. Both `ClockWebhookService` and `ClockWorkerService` now route their `'missing'` branch through a `recreateMissingJob()` method that reads the snapshot, creates the job, and performs this guarded reset — replacing the old blind `transitionEventStatus(..., { clearToken: true })` call entirely for this path (terminal writes elsewhere still use `clearToken` safely, since those are already guarded by `requireToken`). A worker still actually running an attempt claimed under the *old*, now-disappeared job (its Redis job entry can vanish — retention, manual intervention — while its handler keeps executing) is unaffected by any of this: its own eventual finalize remains independently guarded by `requireToken` against its own captured token, regardless of what the reset did or didn't do to the row in the meantime.

**Proof through the real production methods, forcing the exact interleavings, not a reimplementation.** `test/clock-webhook-recovery.e2e.spec.ts` gained two tests exercising `ClockWorkerService`'s and `ClockWebhookService`'s actual `recreateMissingJob`/`readProcessingSnapshot`/`resetForJobRecreation` methods (not hand-assembled SQL): one takes a real snapshot, creates the real replacement job, lets the app's own live worker claim it for real (gated so it pauses right after claiming), then calls the real reset with the pre-claim snapshot and asserts it correctly no-ops (0 rows) and leaves the real claim's token untouched, then releases the gate and confirms hydration still finalizes correctly end to end — proving the transactional hydration fencing and atomic parking from the second/third corrections remain intact. The other drives `ClockWebhookService.recreateMissingJob()` and `ClockWorkerService.reconcileStuckEvent()` concurrently via `Promise.all` against the same row and asserts the outcome is never corrupted regardless of how the real interleaving lands: exactly one BullMQ job exists (BullMQ's own `addStandardJob` Lua script dedups concurrent `add()` calls for the same jobId atomically — verified directly against the installed `bullmq@6` source), the row's ownership is never null'd out from under a real claim, and exactly one booking is ultimately applied. The existing "missing-job recreation" test was also rewritten to drive the real sweep path (`reconcileStuckEvent`) end to end rather than asserting on manually-constructed SQL calls that no longer match the current implementation.
